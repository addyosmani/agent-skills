# W1-P4 - Jira MCP registration

## Intent

Ship Stage B of the Foreman Line: the capability that takes an approved parcel set + Epic/Story tree and **registers** it as real Jira issues, then writes the bidirectional SHA-permalink links that make the spec and the ticket point at each other (SPEC-CONVENTION §5). This is the parcel that turns "approved for registration" (the W1-P3 approval record) into tracked delivery artifacts, and it is the goal's critical parcel because it is the first live exercise of an agent Jira-**write** path. It owns four load-bearing guarantees, all mechanical, none conventional: (1) a **default-deny sandbox gate** that pins the destination project to exactly `KONE` and stamps every created issue with the `mcp-test` label AND a `[TEST]` summary prefix, asserted before any create call, with a negative-control probe (charter F4, D3-amended); (2) a **hash-refusal** that refuses to register if the current artifact no longer hashes to the P3-approved `approvedHash` (charter F7); (3) the **registration write-back protocol** - create tree -> back-fill `ticket:` frontmatter -> commit -> push -> permalink bound to the pushed post-key SHA (charter F5); and (4) the **Stage-B receipt** appended to the approval record's chain (charter F8). It is built on the write-direction `plugins/audit-suite/skills/jira-integration` base (charter F2); the §5 SHA-permalink linking is net-new on top.

The load-bearing design fact this parcel exists to enforce: **the sandbox gate is mechanical, not a convention.** No argv, no environment variable, no adapter, no code path reaches a Jira create without the project-key allowlist, the `mcp-test` label, and the `[TEST]` prefix all asserted first - and an attempted write to any non-`KONE` key is refused by the gate (a thrown error with zero adapter calls), never by good behaviour.

- **Hash-refusal (charter F7; coordinator ruling Q4):**
  - Consume the shipped `approval` package's exported `computeApprovalSubject` (and `canonicalize`/`sha256Hex`) **read-only** via relative ESM (`import { computeApprovalSubject } from '../../approval/src/index.js'`) - **no fourth vendored canonical/hash copy.** This is strictly better than vendoring: it is the identical code path that produced `approvedHash`, so there is zero parity-drift risk and no parity vector to re-pin.
  - Read the approval record at `plugins/foreman-line/docs/specs/active/<slug>.approval.json` (shipped `ApprovalRecord` shape: `approvedHash`, `subject`, `correlation`, `receipt` = `{hash, locator}`). Re-derive the composite subject hash from **current on-disk content** via `computeApprovalSubject(record.subject.projectedResult, repoRoot).approvedHash` and refuse (typed `HashMismatchError`, exit code `1`) if it differs from `record.approvedHash`.

- **Prior-registration / reconcile ordering (coordinator ruling Q5 - RATIFIED design fact, dual-review probe target):**
  - The write-back mutates the referenced spec `.md` files (`ticket: KONE-TBD` -> real key), which changes their content hash - so a naive F7 re-derivation would refuse **every** re-run after the first. Resolution: a **prior-registration detection step runs before F7.** F7 is a **first-registration precondition**, evaluated only while content is still in its approved state.
  - **Detection MUST key off the Stage-B receipt for the same `workflowId`** (does `docs/receipts/<workflowId>/000001-B-registration-result.json` exist and validate as part of a valid chain with the genesis?), **not merely off non-TBD ticket keys.** If the Stage-B receipt exists for this `workflowId` -> **reconcile mode**: verify/refresh the bidirectional links idempotently, create nothing, and do **not** run F7 against the (legitimately) back-filled content. If it does not exist -> run F7 against current content, then proceed to create.
  - **The abuse this ordering must not open (dual-review focus):** reconcile mode must be unreachable for genuinely-unapproved content. Because detection keys off the workflowId's Stage-B receipt (minted only by a completed first registration that itself passed F7), a caller cannot fabricate reconcile mode by hand-editing `ticket:` keys into unapproved specs - there is no Stage-B receipt for a workflowId that never registered. The order is: prior-registration(Stage-B receipt) check -> else F7 -> else create.

- **Write-back protocol (charter F5; coordinator ruling Q6 - 12-step ordering, RATIFIED):**
  0. `assertRegistrationGate` is armed for every subsequent create/update (project-key + label + prefix).
  1. Load the approval record -> `workflowId` (= `correlation.workflowId`), `approvedHash`, genesis `ReceiptRef` (`record.receipt`).
  2. Prior-registration / idempotency check (above): reconcile vs. first-registration.
  3. F7: re-derive + refuse on mismatch (first-registration path only).
  4. Create Epic, then Stories (search-first idempotent per `jira-integration`: JQL search the project for the stable id in the summary; exactly one match -> update; none -> create; multiple -> stop and report). Story -> Epic via `parent`.
  5. Back-fill `ticket:` frontmatter in each referenced spec `.md` (KONE-TBD -> the real key), in `parcelSpecRefs` order.
  6. Commit the back-fill (this is the commit whose SHA the `commit->ticket` permalink binds).
  7. Push.
  8. Capture the pushed post-key SHA (`git rev-parse` of the pushed ref, after push confirms).
  9. Build the `commit->ticket` permalink bound to that SHA; write the `ticket->commit` link into Jira (a remote link / comment carrying the permalink, per §5) - this is a Jira **update**, subject to the same gate and idempotency.
  10. Mint + write the Stage-B receipt (below).
  11. Emit the `RegistrationResult` (`ticketKeys` + both-direction `links`), re-validated against the frozen `registrationResultSchema`, persisted at `active/<slug>.registration.json`.
  - **Rollback / failure policy (RATIFIED):** **no destructive undo of created tickets** (deletion is outward-facing and noisy to undo). On any post-create failure, **STOP, report exactly what landed vs. what did not (by ticket key / step), and leave a re-runnable idempotent state** - the search-first idempotency guarantees a re-run creates no duplicates. Specific seams: created tickets but the frontmatter commit fails -> tickets exist, re-run finds+updates them, back-fill resumes; pushed but the `ticket->commit` link write fails -> the SHA exists, re-run recomputes the deterministic permalink and re-writes the link (idempotent update).

- **Commit shape (coordinator ruling Q7 - two commits in the proof PR, RATIFIED):** the permalink must bind the pushed post-key SHA, and the Stage-B receipt records the `RegistrationResult` (which needs that SHA) - so the receipt cannot ride the same commit whose SHA the permalink binds. **Commit 1** = frontmatter back-fill (the permalink-bound SHA). **Commit 2** = the Stage-B receipt + the `RegistrationResult` sidecar at `active/<slug>.registration.json` (non-`.md`, never trips the spec-linter - mirrors the approval sidecar). Both land in this parcel's proof PR.

- **Stage-B receipt (charter F8; coordinator ruling Q8 - RATIFIED):**
  - Exactly one `ReceiptDocument` appended at registration: `kind: 'stage'`, `stage: 'B'`, `sequence: 1`, `prevHash` = `approvalRecord.receipt.hash` (the genesis hash), `correlation` = `approvalRecord.correlation` (**same `workflowId`** - the chain key), `subjectKind: 'RegistrationResult'` (slugs to `registration-result`), `subject` = the `RegistrationResult` payload (`ticketKeys` + both-direction `links`), `signature: null`, `schemaVersion: '1'`, `hash = sha256Hex(canonicalize(<this document with the \`hash\` key removed>))` (reusing `approval`'s exported `canonicalize`/`sha256Hex`, the shipped hash domain).
  - Stored at the shipped `receiptPath(workflowId, 1, 'B', 'RegistrationResult')` -> `docs/receipts/<workflowId>/000001-B-registration-result.json`, POSIX separators, repo-root-relative. Validated with the shipped `validateReceiptDocument` before write. **`validateChain([genesis, stageB])` MUST pass** (contiguous `sequence` `0,1`; `stageB.prevHash === genesis.hash`; identical `workflowId`/`correlationId`).
