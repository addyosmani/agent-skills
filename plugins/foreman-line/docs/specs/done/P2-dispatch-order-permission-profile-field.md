# P2 - DispatchOrder `permissionProfile` Field

## Intent

Add exactly one optional, additive field - `permissionProfile?: string` - to the `DispatchOrder` contract in `plugins/foreman-line/contracts/`, so a dispatched parcel can carry the *name* of the permission profile resolved for its worktree onto its Stage-C receipt for Trust Wall auditability. This is the goal charter's single frozen-contract touch (charter D2), scoped **exactly** to three artifacts: the `DispatchOrder` **type**, its **JSON schema**, and the **parity/propagation tests** that prove type and schema never drift. The field's *value* is drawn from the permission-profile-name vocabulary P1 shipped (`PROFILE_NAMES` in `plugins/foreman-line/permission-profiles/`), but at this contract layer the value is an **opaque, well-formed string** - identical in spirit to how `routingDecisionRef` is a bare reference string and `injectedSkills` are opaque skill-name strings today. Enum-binding the value against the registry is P4's job (spec-linter), never this package's.

This parcel ships a **type-level contract only**. No runtime code anywhere in this repo constructs a `DispatchOrder` (dispatch automation is future W2-P3 work; charter plan-review F-E), so "carried on the DispatchOrder receipt" is a *type-and-schema* guarantee within this goal, not an exercised end-to-end data flow. This spec must not imply otherwise, and a builder who finds themselves standing up a `DispatchOrder` producer to make the field "real" is committing scope creep into W2-P3 - that is a **stop-and-report**, not a natural next step.

This is the single genuinely frozen contract package in the repo; the standing "modifying frozen contracts is a loop-stop" rule is suspended for this parcel **only** by charter D2's narrow exception, and only for the exact three-artifact surface below.
- **Stack:** TypeScript, ESM-only, Node >=22 (repo root `engines.node` requires >=24.11.1; the live toolchain reports `v24.11.1`). Tests via `node --test` driven through `tsx` (`tsx --test tests/*.test.ts`, the package's existing `npm test` script). Lint/format with `biome`.
- **Standing rule (binding, W0-P1 rework lesson):** ajv's `JSONSchemaType` is banned as a schema authority anywhere in this repo. The schema edit MUST stay a hand-authored `SchemaObject`, consistent with the existing `dispatchOrderSchema` in `src/stages/c-dispatch.ts`. Do not introduce type-derived schema generation.
- **Dual representation, no drift (existing package discipline):** `DispatchOrder` ships as (1) a TypeScript `interface` and (2) a hand-authored `SchemaObject` (`dispatchOrderSchema`), with the committed `schemas/*.json` files serialized from the typed source by `src/generate.ts` (`npm run generate`) and proven byte-identical by `tests/parity.test.ts`. The value stays opaque here, exactly as `routingDecisionRef`/`injectedSkills` are opaque references today. `package.json.dependencies` must remain unchanged (`{ajv}` only).

### The exact three-artifact surface (charter D2 - nothing beyond this)

**Artifact 1 - the `DispatchOrder` type** (`src/stages/c-dispatch.ts`):

- Add one property to the `DispatchOrder` interface: `readonly permissionProfile?: string`.
- **Placement (decision #2, recommended resolution):** appended as the **last** property, immediately after `injectedSkills`. Reasoning: (a) property order is semantically irrelevant to validation but *is* significant to the serialized JSON byte output and therefore to diff cleanliness on a frozen contract - tail-append yields a minimal, obviously-additive diff with no reflow/reorder of existing fields or their serialized blocks; (b) the type's doc-comment already groups `routingDecisionRef` and `injectedSkills` as the "opaque here, resolved elsewhere" cluster, and `permissionProfile` is the same species (a name resolved by P1's registry, applied by P3's emitter, opaque at this layer) - appending after `injectedSkills` keeps that opaque cluster contiguous at the tail. (The kickstarter suggested adjacency to `routingDecisionRef`; tail-append satisfies the same conceptual grouping while producing a cleaner diff, so it is preferred - see Provisional Decisions for the coordinator's override option.)
- **Doc-comment (decision #7, recommended resolution):** minimally extend the existing JSDoc on `DispatchOrder` so it names `permissionProfile` as also opaque/resolved-elsewhere. Leaving the comment stating only `routingDecisionRef`/`injectedSkills` are opaque, after adding a third opaque field, would be an inaccuracy shipped into a frozen contract. This edit is within the authorized "DispatchOrder type" surface (same declaration, same file, no shape change beyond the one field).

**Artifact 2 - the JSON schema** (`schemas/dispatch-order.schema.json`, plus its generated composed form - see decision #5):

- In `dispatchOrderSchema` (`src/stages/c-dispatch.ts`), add one property to `properties`: `permissionProfile: { type: 'string', minLength: 1 }`.
- **Do NOT add `permissionProfile` to the schema's `required` array** - the field is optional; adding it to `required` would be a breaking change and a defect.
- `additionalProperties: false` stays as-is (unknown fields still rejected; `permissionProfile` is now a *known* optional field).
- **`minLength: 1`, no whitespace-rejecting pattern (decision #8, recommended resolution):** match the sibling string fields (`parcelRef`, `stepZeroRestatement`, `routingDecisionRef`) exactly. Do NOT add a whitespace-only-rejecting regex - no sibling contract field does, and non-whitespace / registry-name validation is P4's (spec-linter, on frontmatter) concern, not this contract's. D2 authorizes a "plain string," not a constrained format.
