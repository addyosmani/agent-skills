# W0-P5 - Skill Injection Matrix Schema + Validator

## Intent

Define the frozen JSON Schema (and matching TypeScript type) for `skill-injection.yaml` - the policy-as-code artifact that governs which skills are injected at which pipeline role, per plan §5a - and ship a validator that checks a matrix document against both structure and the semantic invariants §5a already states in prose ("injection is driven mechanically by the parcel's `surfaces:` and task class - no per-dispatch human decision"). Ship the concrete v0 matrix file itself, populated with §5a's illustrative content, so the schema and validator are proven against real content on day one, same discipline as W0-P3's `routing-policy.yaml` and W0-P4's worked receipt fixture. This parcel produces the artifact W2-P5 ("skill injection engine: matrix evaluation at dispatch") will later evaluate against a specific parcel's `surfaces:`/`routing_class:`; it does not perform that evaluation. It also *specifies* (in prose, not executable code) the surface-glob resolution semantics W2-P5 must implement, so that later parcel has an unambiguous contract to build against rather than reverse-engineering intent from this document's schema alone.

This is the last W0 parcel. Once it ships, W0's exit criterion - "all contracts reviewed and merged; downstream waves build against frozen interfaces" - is met.

A test MUST assert that `package.json`'s `dependencies` keys equal exactly `{ajv, yaml}` - machine-enforced per the W0-P3/W0-P2 pattern.

Therefore: **W0-P5 ships as a fourth copy of the same pattern - no shared package is extracted in this parcel.** Consolidation into a shared internal package is a future, separately-scoped parcel, to be taken up once the deferred permission-profile-registry parcel ships as a fifth consumer and the pattern has proven stable across all five - same "extract only once a second team wants it, never build the platform first" logic already applied to the permission-profile registry's own long-term direction.
- **No cross-package import:** this package does NOT import from any sibling `plugins/foreman-line/*` package (`contracts`, `routing-policy`, `receipts`, `spec-linter`) - same self-containment rule W0-P2's spec-linter and W0-P3's routing-policy followed. The shared-validator ruling above means duplication is deliberate, not an oversight to "fix" by importing a sibling.
- **`SkillInjectionMatrix` shape (dual representation - TypeScript type + JSON Schema + parity test, same discipline as W0-P1/W0-P3/W0-P4):**
  ```ts
  type GlobPattern = string   // '*' or '<prefix>/*' - see Surface-Glob Resolution Semantics below
  type SkillName = string     // opaque identifier; existence is NOT validated - see Constraints, skill-name well-formedness

  interface RoleSkillMap {
    readonly [glob: GlobPattern]: readonly SkillName[]
  }

  interface CoordinatorSkills {
    readonly rework_first: readonly SkillName[]
  }

  interface IntegrationSkills {
    readonly jira: readonly SkillName[]
  }

  interface SkillInjectionMatrix {
    readonly builder: RoleSkillMap
    readonly verifier_harness: RoleSkillMap
    readonly adversarial_reviewer: RoleSkillMap
    readonly coordinator: CoordinatorSkills
    readonly integration: IntegrationSkills
  }
  ```
- **Top-level key enumeration: LOCKED CLOSED (coordinator-ratified 2026-07-15).** The five top-level keys (`builder`, `verifier_harness`, `adversarial_reviewer`, `coordinator`, `integration`) are the complete enumeration. The schema sets `additionalProperties: false` at the top level and `required: [builder, verifier_harness, adversarial_reviewer, coordinator, integration]` - all five keys MUST be present; a matrix document missing any one is a schema violation, not a silently-defaulted "no rules for this role." This is a deliberate divergence from `surfaces:`'s semi-controlled-vocabulary precedent (SPEC-CONVENTION §4.7): `surfaces:` describes an open-ended filesystem namespace where a novel prefix is expected and made visible via advisory warning, not blocked. These five keys instead name fixed pipeline roles enumerated by the plan itself (builder/harness/reviewer/coordinator/integration) - a sixth role appearing is a Line architecture change requiring a spec amendment, not a vocabulary extension an advisory warning should merely flag. Hard rejection, not an advisory path, is correct here.
  - **Role-map presence vs. emptiness (this parcel's own ruling, surfaced here for adversarial review - not previously asked of the coordinator):** each of `builder`/`verifier_harness`/`adversarial_reviewer` MUST be present as a key but MAY be an empty object (`{}`), meaning "no injection rule currently defined for this role" - this is an explicit, visible statement of "nothing yet," not an omission. What is NOT permitted: a present glob-pattern key whose skill-name array is empty (`'*': []`) - see semantic invariants below. The distinction is deliberate: a missing top-level key or an empty array under a present key would each be a different flavor of "silently resolves to no skills injected" that plan §6's "declared, never derived-by-omission" logic argues against; requiring the *role map* to be explicitly present (even if empty) while forbidding an *explicitly present but empty skill list* closes both silent-injection ambiguities named in the kickstarter's adversarial-focus list.
  - `coordinator.rework_first` and `integration.jira` are each `additionalProperties: false`, with their single nested key `required` and its value a non-empty `SkillName[]` - no empty-object variant here, since §5a shows no illustrative case where the Coordinator or the Jira integration point has zero skills; if that need arises it is a spec amendment, not a schema gap.
- **Surface-glob pattern syntax (structural, enforced by JSON Schema `propertyNames`):** a glob-pattern key in `builder`/`verifier_harness`/`adversarial_reviewer` MUST be either exactly `'*'` or match `^[^*]+/\*$` (a non-empty, star-free prefix followed by a literal `/*`) - e.g. `'ui/*'`, `'tenancy/*'`, `'plugins/foreman-line/*'` are valid; `'ui/*/checkout'`, `'**'`, `'ui*'`, and the empty string are not. This is prefix-style glob matching only; no mid-string or suffix wildcards are supported in v0.
- **Surface-Glob Resolution Semantics (specified here in prose per coordinator ruling; NOT executed by this parcel - see Validator Scope below and Out of Scope):** given a parcel's `surfaces:` array (SPEC-CONVENTION §4.6, non-empty array of repo-relative paths/globs) and a role's `RoleSkillMap`, the resolved skill set for that role is the **union, deduplicated by skill name**, of every glob pattern's skill array where the pattern is `'*'` OR the parcel has at least one `surfaces:` entry that matches the glob's prefix at a **path-segment boundary** - i.e., the entry either equals the prefix exactly or starts with the prefix followed by a literal `/` (the glob with its trailing `/*` stripped, e.g. `'ui/*'` -> prefix `ui`). This is deliberately **not** a raw string-prefix test: `surfaces: [uix/foo.ts]` does NOT match `'ui/*'`, even though the raw string `'uix/foo.ts'` starts with the substring `'ui'` - only a path-segment match counts (corrected 2026-07-16, coordinator-ratified, after adversarial review B correctly flagged the original phrasing as ambiguous between raw-string-prefix and segment-boundary semantics; the README's own worked example always meant segment-boundary, this line now says so explicitly). This is additive, not override-based: §5a's own worked example - "every parcel gets `test-coverage`... `ui/*` parcels additionally get `kds-figma`" - reads as union ("additionally"), not most-specific-wins or first-match. **W2-P5 owns the executable implementation of this rule**; this parcel's README states it as the contract W2-P5 must satisfy, and ships zero code that runs it. This boundary is the single most important line in this spec and is repeated in Out of Scope and the Verification Plan's adversarial-focus questions.
- **Skill-name well-formedness only - existence validation is OUT OF SCOPE (coordinator-ratified 2026-07-15).** Skill names (`test-coverage`, `kds-figma`, `kds-sweep`, `tenant-isolation`, `code-review`, `build-fix-loop`, `jira-workflow`, etc.) are validated only as non-empty, non-whitespace-only strings - opaque identifiers at this layer, structurally identical to how `permission_profile:` is validated in W0-P2's spec-linter. Cross-checking that a referenced skill name actually exists as an installed skill is explicitly deferred, for three reasons discovered during shaping: (1) this repo's own `skills/` directory (`dotnet/`, `get-app-specs/`, `goal/`, `jira-workflow/`, `modernize/`, `parcel-compiler/`, `parcel-driven-development/`) does not contain most of §5a's illustrative skill names - they are expected to resolve against the *deployed* skills location (`~\.claude\skills\`, per §5a's own framing: "the rack of tools hanging above each station... deployed at `~\.claude\skills\`"), which is a different directory on a different machine than wherever this validator runs; (2) a same-repo existence check would therefore check the wrong directory, and a check against the deployed path is a dispatch-time/runtime-environment concern, not a static schema check a CI job can run reproducibly against repo content alone; (3) the deployed skills directory changes independently of this package's release cycle - a validator that hard-codes today's skill list would go stale the moment a skill is added or removed, exactly the stale-list problem the coordinator flagged at shaping. Existence-checking is named explicitly in Out of Scope as a W2-P5/CI concern.
- **Frozen contracts and sibling packages are untouchable:** `plugins/foreman-line/contracts/` is out of bounds for modification. `plugins/foreman-line/routing-policy/` and `plugins/foreman-line/receipts/` are frozen, read-only reference only - never imported from or modified, per the shared-validator ruling above.
- **Validator surface:** a single `validate <path>` CLI command, thin wrapper over an exported library function `validateSkillInjectionMatrix(doc): ValidationResult`. No `resolve`/`evaluate` command - resolving what skills a given parcel's `surfaces:` + `routing_class:` would actually inject is dispatch-time evaluation (W2-P5), not static validation, and is explicitly not built here, mirroring W0-P3's "no `explain` command" and W0-P4's "no `receipt verify`" precedent.
- **Exit-code contract (frozen by this parcel, mirrors pcc/routing-policy/receipts/spec-linter style):** `0` valid; `1` schema or semantic-invariant violation (stderr lists every violation found, not just the first); `2` usage error (missing/unreadable path, bad invocation).
- **Branch/worktree (defects_lessons #9):** builder works on a named feature branch `feat/foreman-line-W0-P5`, isolated in its own worktree at `C:\Repos\foreman-line-W0-P5` - never directly in the main working tree. This line goes into the dispatch kickstarter verbatim; it is not ambient knowledge.
- **Deterministic-pass environment (defects_lessons #10):** verification runs in PowerShell only. `node -v` is checked first, before any other command, and must report >=22 for this package (repo root `package.json` `engines.node` requires >=24.11.1, per the standing rule). Shell selection is a standing rule, not left to discovery mid-build.
- **PowerShell pipeline exit-code lesson (defects_lessons #11), carried forward from W0-P2's Verification Plan:** CLI exit-code tests capture output in full before reading `$LASTEXITCODE` - never truncate a pipeline whose exit code is under test.
- All source is `readonly`/immutable-shaped where applicable; the schema describes a matrix document's shape, not mutable runtime state.

## Acceptance Criteria

1. `npx tsc --noEmit` passes on the skill-injection package.
2. `SkillInjectionMatrix` (and nested `RoleSkillMap`, `CoordinatorSkills`, `IntegrationSkills`) has a matching JSON Schema in `schemas/`, and a parity test proves type <-> schema agreement for all of them.
3. Schema, structural (each with a passing and a rejecting fixture):
   a. All five top-level keys (`builder`, `verifier_harness`, `adversarial_reviewer`, `coordinator`, `integration`) present is required; a document missing any one is rejected.
   b. An unknown sixth top-level key is rejected (`additionalProperties: false`).
   c. A glob-pattern key in `builder`/`verifier_harness`/`adversarial_reviewer` not matching `^\*$|^[^*]+/\*$` (e.g. `'ui*'`, `'**'`, `''`) is rejected.
   d. An unknown key nested under `coordinator` (other than `rework_first`) or under `integration` (other than `jira`) is rejected.
4. Semantic invariants, each with a passing and a rejecting fixture:
   a. A role map (`builder`/`verifier_harness`/`adversarial_reviewer`) present as an empty object (`{}`) is accepted (explicit "no rule yet").
   b. A glob-pattern key present with an empty skill-name array (`'*': []`) is rejected - "present but empty" is distinct from "role map absent" and both must be visible failures or explicit non-failures per the Constraints ruling, never a silent default.
   c. `coordinator.rework_first` and `integration.jira` each require a non-empty `SkillName[]`; an empty array under either is rejected.
   d. A skill name that is an empty string or whitespace-only is rejected, in any of the five roles' skill-name arrays.
   e. A matrix document produced by parsing YAML containing duplicate keys at the top level, or duplicate glob-pattern keys within a single role map, is rejected - the `yaml` package is invoked with its duplicate-key-detection option enabled (not the silent last-wins default) so a duplicate key is a parse-time error surfaced as a CLI exit `1`/`2` violation, never a silently-collapsed document that then passes schema validation unaware a key was dropped.
5. The shipped `skill-injection.yaml` v0 file validates against `skill-injection.schema.json` with zero errors, and reproduces §5a's illustrative content: `builder` with `'*': [test-coverage]` and `'ui/*': [kds-figma]`; `verifier_harness` with `'*': [test-coverage.check]`, `'ui/*': [kds-sweep]`, `'tenancy/*': [tenant-isolation]`; `adversarial_reviewer` with `'*': [code-review]`; `coordinator.rework_first: [build-fix-loop]`; `integration.jira: [jira-workflow]`.
6. CLI `validate` command: exits `0` on the shipped valid matrix; exits `1` with every violation listed on stderr (not just the first) against fixtures for each of AC3-AC4's rejecting cases, **except AC4e** (duplicate keys), which is a YAML parse-time failure and is ratified to exit `2` (the parse-error bucket, same as an unreadable file) rather than `1` - clarified 2026-07-16 after adversarial review B correctly flagged the original wording as ambiguous against Constraints' own exit `1`/`2` hedge for AC4e; exits `2` on a missing path, an unreadable file, and AC4e's duplicate-key fixtures.
7. `package.json`'s `dependencies` keys equal exactly `{ajv, yaml}`, enforced by a test reading `package.json`.
8. `biome check .` passes with zero diagnostics.
9. All tests pass via `npx tsx --test`; total test count >= 20.
10. `skill-injection/README.md` documents the schema shape, the top-level-key-closed ruling and its explicit contrast with `surfaces:`'s open vocabulary, the role-map-empty-vs-glob-empty distinction, the surface-glob pattern syntax, the **Surface-Glob Resolution Semantics** as the executable contract W2-P5 must implement (stated in prose, with a worked example), the skill-name-existence-is-out-of-scope decision and its three reasons, the exit-code contract, and the shared-validator/fourth-copy decision - in <= 1.5 pages.
