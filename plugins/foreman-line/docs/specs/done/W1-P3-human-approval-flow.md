# W1-P3 - Human approval flow (CLI)

## Intent

Ship the Stage A **human gate** of the Foreman Line: the CLI capability by which a human reviews the projected parcel set + Epic/Story tree, decides to approve or reject, and - on approval - **binds** the decision to an RFC 8785 canonical hash of the approved spec-set and mints the receipt chain's genesis (Stage-A) receipt. This is the parcel that turns "shaped and projected" into "approved for registration": the artifact W1-P4 later refuses to register against unless the current content still hashes to the approved value (charter F7).

The parcel produces three durable outputs at approval time: (1) an **approval record** sidecar carrying the `approvedHash`, the exact subject manifest that hash covers, the decision, the approver identity, a freshly-minted `CorrelationContext`, and the minted `ReceiptRef`; (2) the **genesis / Stage-A `ReceiptDocument`** written per the W0-P4 locator convention; and (3) nothing else - it flips no spec `status`, writes no Jira, and never mutates a frozen contract or a shipped package.

The load-bearing design fact this parcel exists to enforce: **approval is a human gate** (charter D-plan §2 Stage A). The CLI presents; the human decides. No code path - no flag, no environment variable, no non-interactive invocation - can produce an approval without a live human at an interactive terminal.

- **Canonicalization + hash: vendored, single-file, parity-pinned (coordinator ruling Q1, RATIFIED (b)):**
  - The shipped `receipts` (W0-P4) package **exports no canonicalizer or hasher** by design - its README pins the RFC 8785 (JCS) + SHA-256 algorithm to `skills/parcel-compiler/tool/src/receipts/canonical.ts` + `util/hash.ts` as the sole authority, "cited by reference, never imported, vendored, or re-implemented," and re-implements it independently in its own test-only `tests/support/canonical.ts`. W1-P3 must **compute** hashes at runtime (the F7 `approvedHash` and every `ReceiptDocument.hash`), so it vendors a **minimal `src/canonical.ts` / `src/hash.ts`** into this package (RFC 8785 object-key sort + no-whitespace serialization; `sha256Hex` via `node:crypto` `createHash('sha256')`).

  - **Drift is caught mechanically:** a parity test MUST reproduce the receipts package's frozen worked vector - the `hash` in `plugins/foreman-line/receipts/tests/fixtures/hash-vector-genesis.json` = `06d29ab66ebffd099f4e9031f7c38ffb778a996f6e18726ab8eea30a35f3ee23` - by canonicalizing that fixture's document with the `hash` key removed and hashing it. Any drift of the vendored algorithm from the authority fails this test.
- **The approval subject and `approvedHash` (coordinator ruling Q2, RATIFIED):**
  - The F7 "spec-set" hash covers **both** the projected tree **and the referenced spec files' contents** - not the projected artifact alone. **TOCTOU rationale (state in Intent/here):** if only the projected `<slug>.projected.shaping-result.json` bytes were hashed, a human could edit a referenced `.md` spec after approval and W1-P4 would register changed content against a still-matching hash - the exact time-of-check/time-of-use gap F7 exists to close.
  - The **approval subject** is a canonical composite object:
    ```
    { projectedResult: <the filled ShapingResult payload>,
      specSet: [ { ref: <parcelSpecRef, verbatim>, contentHash: sha256Hex(<spec file bytes>) }, ... in parcelSpecRefs order ] }
    ```
  - `approvedHash = sha256Hex(canonicalize(composite))`. The hash is computed over the **canonicalized payload**, never over the on-disk pretty-printed bytes - so incidental whitespace/formatting can never break a legitimate match, and two different spec-sets can never collide (each spec's content hash and ordered ref are inside the hashed bytes).
- **Approval record sidecar (coordinator ruling Q3, RATIFIED):**
  - Written to `plugins/foreman-line/docs/specs/active/<slug>.approval.json` (a non-`.md` sibling never trips the spec-linter, which collects only `.md` - same rationale as the projected artifact). `<slug>` is the input artifact's slug.
  - Contents: `approvedHash`; the full subject manifest (`projectedResult` reference/summary + `specSet` with per-ref `contentHash`, in order); `decision: "approved"`; an ISO-8601 UTC `timestamp` (trailing `Z`, `ISO_UTC_PATTERN`); the approver identity; the freshly-minted `CorrelationContext` (Q5); and the minted `ReceiptRef` (`{hash, locator}`).
  - **Refuse to overwrite** an existing `<slug>.approval.json` (throw naming the colliding path), mirroring W1-P1/W1-P2 collision policy. A re-approval after amendment (see below) is a deliberate, human-driven act, not a silent clobber.
- **Receipt mechanics (coordinator ruling Q4, RATIFIED - "one document, both roles"):**
  - Exactly **one `ReceiptDocument`** is minted at approval: **the genesis IS the Stage-A receipt.** Per W0-P4 chain semantics, `sequence: 0` / `prevHash: null` is the genesis, minted at Stage A. Field values: `schemaVersion` per the shipped `receiptDocumentSchema`; `kind: 'stage'`; `stage: 'A'`; `claimRef: null`; `sequence: 0`; `prevHash: null`; `timestamp` (ISO-UTC); `subjectKind: 'ShapingResult'` (slugs to `shaping-result` per the receipts README example); `subject` = the approval subject manifest including `approvedHash`; `signature: null` (reserved this wave); `hash` = `sha256Hex(canonicalize(<this document with the \`hash\` key removed>))`.
  - **W1-P4's shaping inherits this reading:** there is one Stage-A receipt (the genesis), NOT two receipts at sequence 0 and 1; W1-P4 appends the Stage-B receipt at **`sequence: 1`** with `prevHash` = the genesis's `hash`, to the same `workflowId` chain.
  - Stored at the W0-P4 locator built by the shipped `receiptPath(workflowId, 0, 'A', 'ShapingResult')` -> `docs/receipts/<workflowId>/000000-A-shaping-result.json`, repo-root-relative, POSIX separators. The minted `ReceiptRef.locator` equals exactly that path; `ReceiptRef.hash` equals the document's `hash`. The minted document is validated with the shipped `validateReceiptDocument` before it is written.
- **Correlation identity (coordinator ruling Q5, RATIFIED):**
  - The projected artifact and `ShapingResult` carry no correlation, and the receipt chain key (`correlation.workflowId`) must be **stable P3 -> P4**. The CLI **generates a fresh `CorrelationContext`** at approval time (`node:crypto` `randomUUID()` for `correlationId`, `sessionId`, `workflowId`, `runId`; each matches the frozen `UUID_PATTERN`) and **persists it in the approval record.** W1-P4 reads `workflowId` from the approval record to append its Stage-B receipt to the same chain. No new dependency (built-in `node:crypto`).
- **CLI surface + human-gate integrity (coordinator ruling Q6, RATIFIED in full):**
  - A `bin`-registered CLI (`approval`) matching the shipped `routing-policy` / `receipts` precedent: `process.argv` parsing, `process.exitCode`, exit codes `0` success / `1` semantic-or-validation failure / `2` usage error (missing/unreadable path, bad invocation, **non-TTY approve**).
  - **`show <slug|path>`** - renders the Epic/Story tree (Epic key + title, each Story key + title, `parcelSpecRefs`) read from the projected artifact. Read-only; mints nothing; **safe in CI / non-TTY**.
  - **`approve <slug|path> [--epic-title <title>]`** - renders the tree, then **requires an interactive TTY** (`process.stdin.isTTY`) **and an explicit typed confirmation phrase** entered by the human. On confirmation: compute `approvedHash`, mint + validate + write the genesis/Stage-A receipt, write the approval record. **There is NO `--yes` / `--force` / auto-approve flag of any kind** (coordinator ruling Q6). If stdin is **not** a TTY (CI, pipe, redirect), `approve` **refuses with exit code `2` and mints nothing** (no receipt, no approval record, no partial write).
  - **`reject <slug|path> [--reason <text>]`** - records a rejection record (`decision: "rejected"`, reason, ISO-UTC timestamp, and the subject hash **for reference only**) but mints **no receipt** and produces **no `approvedHash`** as an approval binding - the receipt chain begins only at approval.
- **Projection invocation (coordinator ruling Q7, RATIFIED - load-if-exists, else project-then-present):**

If it **already exists**, load and render it (the approval subject is the on-disk projected artifact). If it does **not** exist, invoke the shipped `projection` `writeProjectedResult(inputPath, epicTitle)` to produce it first (with `--epic-title` used **only** on this project path), then render.

## Out of Scope

- **W1-P4 (Jira registration):** tree creation, the sandbox project-key allowlist + negative-control probe, the bidirectional SHA-permalink write-back protocol, the **hash-mismatch refusal at registration time** (P4 re-derives `approvedHash` from the current content and refuses if it differs from the approval record's - this parcel produces the hash + record P4 checks, it does not perform the registration-time check), the **Stage-B receipt** (`sequence: 1`, appended to the chain this parcel's genesis begins), and any Atlassian remote MCP interaction. No Jira write of any kind here.
- **W1-P2 (projection):** producing the Epic/Story tree, title/key provenance, the four semantic guards. This parcel **invokes** the shipped `projection` `writeProjectedResult` read-only-by-consumption and adds nothing to it.
- **W1-P1 (shaping):** emitting the input `ShapingResult`, authoring parcel spec drafts, the interactive-shaping skill, the kickstarter template.
- **Cryptographic receipt verification (tamper detection):** this parcel mints and structurally validates receipts; recomputing/verifying an existing chain's hashes from bytes and signature verification remain pcc's future `receipt verify` job (W0-P4 README "the honest limit"). Signing infrastructure does not exist this wave; `signature` is `null`.
- **`status` promotion (draft -> active) or any spec `status` flip:** approval here means approving the parcel set + tree **for registration**; it never touches a spec's `status:` frontmatter. Promotion is coordinator lint + Gate-2 authorization, external to this parcel (coordinator-confirmed closing assumption 1).
- **Modifying any frozen contract or shipped package:** `contracts/`, `shaping`, `projection`, `receipts`, `spec-linter`, `schema-scaffold`, `routing-policy`, `skill-injection`, `permission-profiles`. All read-only. A need to change any of them - especially adding a **Task tier** below Epic/Story (F1), or exporting a canonicalizer from `receipts` - is a loop-stop.
- **Importing pcc canonicalization internals cross-plugin:** the canonicalizer is vendored + parity-pinned (Q1); `skills/parcel-compiler/...` is never imported.
- **Authoring a new stage schema or a new spec-schema field:** this parcel re-validates against the frozen `shapingResultSchema` and validates receipts via the shipped `receiptDocumentSchema`; it defines neither.
- **Adding npm workspace linking to the root `package.json`** or any other root `package.json` change - a Stop-and-Report (SCAF-P1 / W0-P4 precedent).
- **Multi-chain / multi-Epic approval:** one `ShapingResult` = one approval = one receipt chain, mirroring W1-P2's single-Epic topology. Multi-Epic/multi-chain is deferred until a real case exists.
- **CI workflow wiring** (a GitHub Actions step running this CLI) - the package is callable; wiring the workflow is a later wave, same deferral pattern as every prior W0/W1 parcel.
