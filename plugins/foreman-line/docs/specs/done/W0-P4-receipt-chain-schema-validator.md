# W0-P4 - Receipt Chain Schema + Validator

## Intent

Define the frozen shape of the receipt document that `ReceiptRef` (`plugins/foreman-line/contracts/src/envelope.ts:17`, doc-commented "Shape is owned by W0-P4") points to: what bytes `hash` is computed over, how receipts link into a per-parcel chain, where the chain is stored, and how a receipt or chain is structurally validated. This is D8's mandate ("every stage emits an RFC 8785 canonical receipt... the Trust Wall demands a walkable chain") and closes the split PCC-P0 froze open ("W0-P4 owns receipt shape, claim manifest schema, chain linkage, signatures; pcc consumes them later via `receipt verify` and `status`"). Ships as schema + a thin structural validator - no hash recomputation, no signature verification, no cryptographic tamper detection. Those remain pcc's `receipt verify` job by design; this parcel gives that future command a shape to walk and a document to recompute hashes against, not the recomputation itself.

## Constraints

- **Location:** `plugins/foreman-line/receipts/` in `kaseya-one-productivity-tools` (local: `C:\Repos\kaseya-one-productivity-tools`) - sibling to the frozen `plugins/foreman-line/contracts/` and `plugins/foreman-line/routing-policy/`, same foundation tier.
- **Stack:** TypeScript, Node >=22, ESM-only. Tests via `node --test` (`npx tsx --test`). Lint/format with `biome`.
- **Standing rule from the W0-P1 rework (binding on this parcel):** ajv's `JSONSchemaType` is banned as a schema authority anywhere in this repo; every schema is standard JSON Schema draft-07 typed as `SchemaObject`.
- **Runtime dependency allowlist:** exactly one runtime dependency - `ajv` (validation engine only; receipts are pure generated JSON, not YAML-authored, so `routing-policy`'s `yaml` dependency does not apply here). A test MUST assert `package.json`'s `dependencies` keys equal exactly `{ajv}`, machine-enforced per the W0-P3 pattern.
- **Cross-package import (first of its kind in `plugins/foreman-line/`, ratified at shaping):** this package imports `CorrelationContext`, `correlationContextSchema`, `UUID_PATTERN`, `ISO_UTC_PATTERN`, `StageId`, and `STAGE_IDS` from the contracts package's public surface (`plugins/foreman-line/contracts/src/index.ts`). Mechanism, exactly: a filesystem-relative ESM specifier - `import ... from '../../contracts/src/index.js'` from modules under `receipts/src/` (the `.js`-extension-on-`.ts`-source convention the contracts package itself uses internally, resolved by both `npx tsc --noEmit` and `npx tsx --test`). The bare specifier `@foreman-line/contracts` MUST NOT be used: no npm workspace linking exists across `plugins/foreman-line/*` (root `package.json` workspaces only cover `apps/*`/`packages/*`), so a bare specifier does not resolve, and the contracts `package.json` `exports` map plays no part in relative-path resolution. Adding workspace linking or any other change to the root `package.json` to "make it resolve" is out of scope and a Stop-and-Report. This import avoids a second, driftable copy of the branded-id types and the UUID/timestamp patterns. `contracts/` remains untouched; this is read-only consumption of an already-exported surface, not a modification.
- **Canonicalization/hashing authority (by reference, zero code coupling):** `skills/parcel-compiler/tool/src/receipts/canonical.ts` (RFC 8785 / JCS) and `src/util/hash.ts` (`sha256Hex`) are the sole normative algorithm for computing a receipt's `hash`. This package does not import, vendor, or re-implement them - its validator is structural only and never computes a hash from bytes. The hash domain is instead specified precisely enough in prose (below and in the shipped README) that pcc's future implementation and this package's schema agree without ambiguity, proven by a worked test vector (AC8) computed independently against the same documented algorithm.
- **`ReceiptDocument` shape (dual representation - TypeScript type + JSON Schema + parity test, same discipline as W0-P1/W0-P3):**
  ```ts
  type ReceiptKind = 'stage' | 'claim'

  interface Signature {
    readonly alg: string
    readonly keyId: string
    readonly value: string
  }

  interface ReceiptDocument {
    readonly schemaVersion: string          // "1"
    readonly kind: ReceiptKind              // granularity discriminator - ONE type serves both plan §2 Stage D.1 "per-claim" and D8 "per-stage" receipts; multiplicity (1 stage receipt vs. 1-per-claim + 1 aggregate within Stage D) is a runtime creation-time decision for W3, not a contract change - HarnessClaimResult/AdversarialFinding in the frozen d-verification.ts are untouched
    readonly stage: StageId                 // 'A'-'F'; always present, even for kind:'claim' (a claim receipt still belongs to the stage that produced it, typically 'D')
    readonly claimRef: string | null        // non-null iff kind === 'claim'; identifies which claim/finding within the stage
    readonly correlation: CorrelationContext // imported from @foreman-line/contracts; correlation.workflowId is the chain key
    readonly sequence: number               // 0-based, contiguous per workflowId chain; 0 = genesis
    readonly prevHash: string | null        // null iff sequence === 0
    readonly timestamp: string              // ISO_UTC_PATTERN, imported from @foreman-line/contracts
    readonly subjectKind: string            // free-form tag, e.g. "ShapingResult" | "HarnessClaimResult" | "ClosureRecord" - not a closed enum, so new stage/claim payload kinds never require a schema change here
    readonly subject: JsonValue              // the actual receipted content. NOT deep-validated against its originating stage's specific payload schema - that schema is already enforced by W0-P1's frozen contracts at the point the payload was produced; re-validating it here would be redundant, not additional safety
    readonly signature: Signature | null    // reserved; MUST be null in this wave (no signing infrastructure - keypairs, KMS - exists anywhere in this repo yet; deferral is this decision, not silence)
    readonly hash: string                   // sha256Hex(canonicalize(this document with the `hash` key excluded)), bare lowercase 64-char hex, no algorithm prefix
  }
  ```
  `JsonValue` is defined locally in this package (a standard recursive JSON-value type alias, structurally identical to `skills/parcel-compiler/tool/src/receipts/canonical.ts`'s `JsonValue` by design, but not imported - it is a language-standard shape, not proprietary logic, and duplicating a five-line type alias is not the coupling the canonicalization-authority constraint above is guarding against).
- **Hash domain (frozen by this parcel):** `hash = sha256Hex(canonicalize(doc))` where `doc` is the full `ReceiptDocument` JSON object with the `hash` key removed (all eleven other keys included - `schemaVersion`, `kind`, `stage`, `claimRef`, `correlation`, `sequence`, `prevHash`, `timestamp`, `subjectKind`, `subject`, `signature`) and `canonicalize`/`sha256Hex` are exactly the algorithms in the two cited pcc files. Including `prevHash` inside the hashed bytes means altering any earlier receipt in a chain changes that receipt's `hash`, which breaks every later receipt's `prevHash` pointer - this is the chain's tamper-evidence property, even though *detecting* a break requires the cryptographic recomputation this parcel does not perform (pcc's job).
- **Chain semantics:** one chain per parcel, keyed by `correlation.workflowId` (stable across rework retries per W0-P1 AC4 - a `runId` changes per rework attempt, `workflowId` does not). Genesis (`sequence: 0`, `prevHash: null`) is minted at Stage A's `ShapingResult` output - the earliest `StageOutput` in the envelope chain. Rework attempts (Stage D -> C -> D) append further receipts to the same chain; they do not fork a new chain. "Sealed at Stage F" (plan §2 Stage F.2) is a **derived** read, not a stored flag: a chain is sealed iff its highest-`sequence` receipt has `stage === 'F'`. No chain-closing marker or additional hash is written; storage convention (nothing appends after the Stage F receipt in practice) is what "closes" it operationally.
- **Storage convention:** in-repo, git-committed JSON, one file per receipt, at `docs/receipts/<workflowId>/<sequence, 6-digit zero-padded>-<stage>-<subjectKind-slug>.json`, where `subjectKind-slug = subjectKind.replace(/([a-z0-9])([A-Z])/g, '$1-$2').toLowerCase()` (e.g. `ShapingResult` -> `shaping-result`). `ReceiptRef.locator` is exactly that path, POSIX-separator, relative to the repo root. This mirrors SPEC-CONVENTION §1's "specs, prompts, and context are first-class, versioned engineering artifacts" philosophy and gets append-only, diffable history for free from git - no new storage infrastructure. **[Rework amendment, coordinator-ratified]** `receiptPath` guards its inputs at runtime (this parcel freezes the locator convention W3 will write git-committed files against; a guard costs nothing for legitimate input and is expensive to retrofit): `workflowId` MUST match `UUID_PATTERN`; `sequence` MUST be an integer in `0..999999` (the 6-digit zero-padding ceiling, now explicit); `stage` MUST be one of `STAGE_IDS`; the slugified `subjectKind` MUST be non-empty and match `^[a-z0-9-]+$` (reject, don't strip - silent stripping would change locators). Any violation throws a `RangeError` naming the offending argument. The produced path format is unchanged for all legitimate input; the README states these preconditions.
- **Validator surface:** a single `validate <path>` CLI command, thin wrapper over two exported library functions: `validateReceiptDocument(doc): ValidationResult` (schema conformance + the three single-document semantic invariants below) and `validateChain(docs: ReceiptDocument[]): ValidationResult` (the three chain-level invariants below, plus the derived `isSealed` read). `<path>` may be a single receipt JSON file (validates as one document) or a `docs/receipts/<workflowId>/` directory (validates as an ordered chain). Directory semantics (ratified at Step 0): files are sorted ascending by their 6-digit filename sequence prefix - the filename is the sort key, not the payload's `sequence` field. A disagreement between a filename's sequence prefix and its document's `sequence` field is NOT a distinct CLI-layer error in this parcel; it surfaces as whatever chain-invariant violations it causes under AC5, and full locator<->content verification remains pcc's future `receipt verify` job. A directory containing exactly one receipt file validates as a chain (valid iff that receipt satisfies the genesis invariants, AC4b/AC5). A directory containing zero receipt JSON files is a usage error (exit `2`, same class as a missing path - there is nothing to validate). **[Rework amendment, coordinator-ratified]** Two robustness rules bind the library layer: (i) `validateChain` MUST never throw on arbitrary JSON values supplied as chain members - a member that is not a JSON object, or whose `correlation` is not a JSON object, is excluded from the cross-member comparisons it cannot participate in and is reported via its per-document schema violations (which `validateReceiptDocument` already records); the guards in `checkPrevHashPointers`/`checkSequenceContiguity` are explicit, not reliant on accidental `undefined` semantics. (ii) `validateChain([])` returns invalid with a "chain contains no receipts" violation - the library verdict agrees with the CLI's ratified empty-directory semantics rather than vacuously passing; the CLI's exit-`2` usage error pre-empts this path for directory input, and the README documents that division.
- **Exit-code contract (frozen by this parcel, mirrors pcc/routing-policy style):** `0` valid; `1` schema or semantic-invariant violation, every violation listed on stderr, not just the first; `2` usage error (missing/unreadable path, empty chain directory, bad invocation). No CI wiring in this parcel (W4, same deferral as W0-P3).
- **No pcc dependency, no reverse dependency:** this parcel does not import from, depend on, or modify `skills/parcel-compiler/tool/`, and nothing in `skills/parcel-compiler/tool/` may import from this package (that direction was never true and stays that way).
- **Frozen contracts are untouchable:** `plugins/foreman-line/contracts/` - including `ReceiptRef { hash, locator }`'s two-field opacity and `HarnessClaimResult`/`AdversarialFinding`'s current field sets in `d-verification.ts` - is out of bounds for modification. This parcel only *consumes* its exported surface (see cross-package import above).
- **Branch/worktree (defects_lessons #9):** builder works on a named feature branch `feat/foreman-line-w0-p4`, isolated in its own worktree - never directly in the main working tree. This line goes into the dispatch kickstarter verbatim.
- **Deterministic-pass environment (defects_lessons #10):** verification runs in PowerShell only. `node -v` is checked first, before any other command; repo root `package.json` `engines.node` requires `>=24.11.1` and this package's own `engines.node` (`>=22`, matching the `contracts`/`routing-policy` precedent) must be satisfied by whatever the coordinator's machine reports.
- All source is `readonly`/immutable-shaped where applicable; the schema describes a receipt document's shape, not mutable runtime state.

## Acceptance Criteria

1. `npx tsc --noEmit` passes on the receipts package.
2. `ReceiptDocument` (and nested `Signature`) has a matching JSON Schema in `schemas/`, and a parity test proves type <-> schema agreement.
3. Schema validation (strict, `additionalProperties: false`) rejects: a missing required field, `kind` outside `{stage, claim}`, `stage` outside the six `StageId` values, `sequence` negative or non-integer, `prevHash`/`hash` not matching `^[0-9a-f]{64}$` when present as a string, `timestamp` not matching `ISO_UTC_PATTERN`, and an unknown top-level field. **[Rework amendment, coordinator-ratified]** Also rejected, with a fixture: an unknown field nested inside `correlation` - proving the imported `correlationContextSchema`'s `additionalProperties: false` stays load-bearing in this package's composition, so a strictness regression in the imported schema would be caught here.
4. Single-document semantic invariants, each with a passing and a rejecting fixture:
   a. `claimRef` is null when `kind === 'stage'` and non-null when `kind === 'claim'` - a document violating either direction is rejected.
   b. `prevHash === null` iff `sequence === 0` - a genesis with a non-null `prevHash`, or a non-genesis with a null `prevHash`, is rejected.
5. Chain-level semantic invariants, each with a passing and a rejecting fixture, run via `validateChain`:
   a. `sequence` values across the chain are exactly `0..N-1`, contiguous, no gaps or duplicates.
   b. `receipts[0].prevHash === null` and `receipts[i].prevHash === receipts[i-1].hash` for every `i >= 1` (structural pointer resolution - string equality against the prior receipt's *stored* `hash` field; this does **not** recompute that hash from canonical bytes, which stays pcc's job - the Verification Plan names this boundary as a mandated review focus).
   c. every receipt in the chain shares an identical `correlation.workflowId` and `correlation.correlationId`.
   d. **[Rework amendment, coordinator-ratified]** `validateChain` never throws on malformed chain members: rejecting fixtures cover a chain directory containing a scalar-JSON member and one containing a `correlation: null` member, each asserted at the CLI process boundary - exit `1`, every violation on stderr, no stack trace. `validateChain([])` returns invalid ("chain contains no receipts"), asserted at the library layer.
6. `isSealed(chain)` returns `true` iff the highest-`sequence` receipt has `stage === 'F'`, tested against both a sealed and an unsealed fixture chain.
7. `receiptPath(workflowId, sequence, stage, subjectKind)` produces exactly the documented storage path format; a test asserts the format including the slug transform on a multi-word `subjectKind`. **[Rework amendment, coordinator-ratified]** `receiptPath` rejects invalid input per the Storage-convention guard: tests assert a `RangeError` on a non-UUID `workflowId` (including a path-traversal string), a negative `sequence`, a `sequence > 999999`, an invalid `stage`, and a `subjectKind` whose slug contains a path separator or other non-`[a-z0-9-]` character - and that the format for legitimate input is byte-identical to before the guard.
8. A worked hash-domain test vector: a fixed sample `ReceiptDocument` (genesis, `kind: 'stage'`) and its expected `hash`, computed independently against the documented canonicalization + `sha256Hex` algorithm, are checked into a fixture; a test asserts recomputing canonical bytes (via this package's own JCS-equivalent test helper, written solely to validate the fixture, not shipped as a runtime dependency of the validator) reproduces the documented hash string exactly.
9. CLI `validate` command: exits `0` on a valid single receipt and on a valid chain directory; exits `1` with every violation listed on stderr (not just the first) against fixtures for each of AC3-AC5's rejecting cases; exits `2` on a missing path, on an unreadable file, and on an empty chain directory.
10. `package.json`'s `dependencies` keys equal exactly `{ajv}`, enforced by a test reading `package.json`.
11. `biome check .` passes with zero diagnostics.
12. All tests pass via `npx tsx --test`; total test count >= 20.
13. `receipts/README.md` documents the `ReceiptDocument` shape, the hash domain (with the worked test vector from AC8), the storage/locator convention, chain semantics including what "sealed" means, the exit-code contract, the reserved-signature deferral, and the explicit boundary between this parcel's structural chain checks and pcc's future cryptographic `receipt verify` - in <= 1.5 pages.

## Out of Scope

- Implementing pcc's `receipt verify` (hash recomputation against canonical bytes, chain-splice/tamper detection via cryptographic re-derivation, signature verification) or `status` (folding a chain into per-parcel state for display) - both consume this spec's shape later; neither is built here.
- Any runtime receipt *emission* - no stage of the pipeline (A-F) actually writes a `ReceiptDocument` during real dispatch/build/verification in this parcel. That begins in W2/W3 once dispatch and verification exist.
- Signing scheme design (algorithm choice, key management, verification flow) - `signature` ships as a reserved, always-null field only.
- Any modification to `plugins/foreman-line/contracts/`, including `ReceiptRef`'s two-field shape and `HarnessClaimResult`/`AdversarialFinding`'s current fields in `d-verification.ts`. If per-claim receipts ever need an in-band pointer from those types, that is a future, separately-ratified contract amendment - not something this parcel proposes or performs.
- Deep validation of a receipt's `subject` payload against its originating stage's specific payload schema (e.g. confirming a `stage: 'C'` receipt's `subject` actually conforms to `DispatchOrderSchema`). That conformance is already guaranteed by W0-P1's frozen per-stage schemas at production time; re-checking it here is redundant, not additional safety, and this parcel does not attempt it.
- Skill injection matrix schema (W0-P5) - a sibling parcel; no shared abstraction is assumed between it and this package.
- Routing policy evaluation or its schema (W0-P3, shipped).
- CI workflow wiring (a GitHub Actions step running this validator and blocking PRs) - the exit-code contract is documented and callable; wiring the workflow file is W4, same deferral pattern as W0-P3.
- Any dependency on, import from, or modification to `skills/parcel-compiler/tool/` in either direction.
- Trust Wall presentation/UI of a receipt chain (future wave, not named in W0-W5).
- Smart Triage / assignment logic and its taxonomy (W5).

Adversarial review mandated focus questions:
1. **Chain-splice/reorder resistance, honestly bounded:** this spec's chain validator only checks that stored `prevHash` values string-equal the *stored* `hash` of the prior receipt - it never recomputes a hash from canonical bytes. Confirm the spec states this limitation plainly (not just in this Verification Plan) and that no test or README claim overstates what the structural validator actually detects (e.g. it would NOT catch a coordinated edit that rewrites a receipt's content and consistently patches every downstream `hash`/`prevHash` to match - only pcc's future cryptographic recomputation catches that). If any AC or README line implies stronger tamper protection than this, that is a defect.
2. **Hash-domain ambiguity:** is "canonicalize(doc) with the `hash` key excluded" actually unambiguous given `ReceiptDocument`'s field set - specifically, does `subject: JsonValue` (arbitrary nested JSON) canonicalize deterministically under RFC 8785 for every case the schema permits (nested objects, arrays, the `null` cases in `claimRef`/`prevHash`/`signature`)? Verify the worked test vector (AC8) against the *cited* algorithm in `skills/parcel-compiler/tool/src/receipts/canonical.ts` by reading that file, not by trusting this spec's restatement of RFC 8785.
3. **Canonicalization-authority boundary hunt:** confirm zero runtime import from `skills/parcel-compiler/tool/` exists anywhere in the shipped package (grep the built package, not just this spec's prose promise) and that AC8's "JCS-equivalent test helper" is genuinely test-only, never exported from `src/index.ts` or referenced by `validateReceiptDocument`/`validateChain`.
4. **W0-P1 non-pre-emption hunt:** confirm no field is added to, or type is redefined for, `ReceiptRef`, `HarnessClaimResult`, or `AdversarialFinding` anywhere - types, test fixtures, generated schemas, or README examples - the same hunt PCC-P0 and W0-P3's reviews ran for their respective frozen-contract boundaries, applied here to both W0-P1 and this parcel's own new frozen surface.
5. **Cross-package import precedent:** this is the first import across `plugins/foreman-line/*` siblings. Confirm the import is genuinely read-only (no re-export that widens `@foreman-line/contracts`'s public surface, no modification of files under `contracts/`) and that the relative-path mechanism actually resolves correctly under `npx tsc --noEmit` and `npx tsx --test` without requiring an undocumented workspace change to the root `package.json`.
