## Objective

Ship a reviewed, named permission-profile registry (allow/ask/deny + network + directory envelopes per role) and a dispatch-time mechanism that installs the resolved profile into a parcel worktree's `.claude/settings.local.json` **before** any builder or reviewer session launches, **launched via the exact mechanism pinned in D9-amendment below**. This makes "reviewer never fixes, never commits" a **structurally reduced, mechanically-enforced-where-loaded** capability rather than only a directive sentence — the plan-level review (F-A, F-B) established that "missing capability" as originally worded overstates what deny-first Claude Code settings can guarantee against a Bash-capable session or a session that never reloads worktree-local settings, so this goal ships the strongest honestly-achievable version of that claim, with its limits documented, not glossed over. It also gives `SPEC-CONVENTION.md`'s `permission_profile:` field (added optional-until-registry by W0-P2) a real authority to reference instead of an aspirational one.

## Exit criterion

All four parcels shipped, merged, and Stage-F closed (specs → `done/`, worktrees/branches removed, lessons appended if earned, charter/carryover updated). `permission_profile:` is then usable end-to-end: named in the registry (P1) → referenced in a spec and enforced by lint (P4) → **type-carriable** on the `DispatchOrder` receipt (P2) → actually installed into the builder's worktree before the session starts (P3), **with the installed envelope proven to bite by P3's live capability probe** — not merely asserted by schema validation. `COORDINATOR-PATTERN.md`'s dispatch-table envelope column reads as actual, not aspirational, and the deferred-parcel note is marked taken up.

**Two scope limits, stated honestly rather than implied away (plan-review F-E, F-G):**
- **P2 ships the field's type contract only.** No runtime code anywhere in this repo currently constructs a `DispatchOrder` (dispatch automation is future W2-P3 work) — so "carried on the DispatchOrder receipt" is a type-level guarantee within this goal, not an exercised end-to-end data flow. P3's write-denial probe does not depend on P2 at all; only the audit-stamp claim does. If a P2 or P3 builder finds themselves standing up a `DispatchOrder` producer to make this "real," that is scope creep into W2-P3 and is a stop-and-report, not a silent extension.
- **This goal delivers the envelope mechanism, not its guaranteed application.** Nothing forces a coordinator to invoke P3's wrapper instead of a bare `git worktree add`; skipping it installs no profile. Mandatory-invocation enforcement belongs to future dispatch automation. The exit criterion is "mechanically enforceable when the coordinator runs the wrapper," not "separation of duties is now automatically guaranteed regardless of coordinator action" — do not let closing this gap become a silent fifth parcel.

## Dispatch-mechanics note (operational consequence of D9-amendment(a))

Every prior W0 parcel (per the carryover) was built by "fresh background agents" — i.e., this coordinator's own Agent/Task-tool subagents. **D9-amendment(a), as narrowed, forbids that dispatch shape only for P3's builder and reviewer sessions** (and P3's live capability-probe), since a subagent shares the coordinator's already-loaded settings and would never exercise the worktree-local envelope at all — the exact placebo F-A warned about, one level up, for the one parcel whose job is to prove the envelope bites. P3's builder/reviewer must instead be **top-level `claude` CLI sessions** (a separate terminal/window, cwd = the parcel worktree, normal permission mode) — either Clint-driven sessions or sessions the coordinator starts as a genuinely separate process, not an in-session Agent-tool call. **P1, P2, and P4 have no such restriction and dispatch normally as Agent-tool background subagents**, same as W0. This is a real departure from W0 practice for P3 only, called out here so it isn't silently reverted to habit at P3's dispatch time — and equally so the coordinator doesn't over-apply it to parcels where it serves no safety purpose (as happened on first pass with P1).

## Stop conditions

- Any P2 finding or rework that would touch anything beyond D2 (amended)'s surface (the `DispatchOrder` type, its JSON schema and that schema's generated composed derivative, and the parity/propagation tests — all solely to add the one `permissionProfile?: string` field), or touch any other file in `plugins/foreman-line/contracts/` — that is outside D2's exception and is a stop-and-report.
- Any need to modify the other frozen contracts/shipped-and-closed packages (`routing-policy`, `receipts`, `spec-linter` beyond P4's narrow enum change, `skill-injection`).
- A tripwire fires twice on the same parcel (test count, wrong-shaped claim, false closure).
- A security-relevant finding triage cannot close within the parcel.
- Anything outward-facing beyond the authorizations above (other repos, repo settings, force pushes — all denied).
- Queue empty: all four parcels shipped and closed (exit criterion met).
