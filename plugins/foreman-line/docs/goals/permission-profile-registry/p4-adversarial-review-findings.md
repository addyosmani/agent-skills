## Additional verification: the pre-existing test-failure claim

The builder's completion claim states there is "one pre-existing test failure in `tests/cli.test.ts` ... failing because W0-P5's spec has `permission_profile: null` ... unrelated to the enum." I verified this by checking out `7feeb56`'s (pre-P4) version of `plugins/foreman-line/spec-linter/` over the current tree and re-running `npm test`.

**Confirmed as pre-existing and unrelated to the enum, but the claim's framing understates its scope.** The failing test is `exit 0 (with advisory warning) on all four shipped docs/specs/done specs, directory mode` (`tests/cli.test.ts:45`), and it fails **identically in shape** on both commits: it runs `validate` against the live `docs/specs/done/` directory (not a hardcoded fixture list — it globs whatever is on disk), and that directory now also contains `P1-permission-profile-registry-schema.md`, `P2-dispatch-order-permission-profile-field.md`, and `P3-dispatch-time-emitter.md`, all of which carry `permission_profile: null` (P1/P2/P3 predate the registry's own field being populate-able, so they're `null`, same as W0-P5). Pre-P4, all four of {P1, P2, P3, W0-P5} produce `/permission_profile must be string` (the `type: string` structural check, present before P4). Post-P4, the same four files produce the same `must be string` error **plus** a new `must be equal to one of the allowed values` line each — an extra message from the added `enum`, not a new failure, since these files were already failing that assertion pre-P4. The assertion location, failure count (1 failing test), and root cause (docs/specs/done growing to include specs with `permission_profile: null`, which the `type: string` check already rejected before this parcel) are identical across both commits.

So: the claim is **directionally correct and the "unrelated to the enum" conclusion holds**, but "because W0-P5's spec has `permission_profile: null`" is misleading singular framing — W0-P5 is one of four files (P1, P2, P3, W0-P5) that trip this same pre-existing assertion, and P1/P2/P3 are arguably the more relevant ones since they're this very goal's own shipped specs. This is a completion-claim precision defect, not a code or test defect — flagging it so the coordinator doesn't repeat the narrower framing at Stage-F closure.
