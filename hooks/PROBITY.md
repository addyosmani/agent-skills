# probity enforcement templates

Hard enforcement for three of this catalog's disciplines — [`test-driven-development`](../skills/test-driven-development/SKILL.md), [`ports-and-adapters`](../skills/ports-and-adapters/SKILL.md), and [`acceptance-testing`](../skills/acceptance-testing/SKILL.md) — via [Probity](https://github.com/nizos/probity), a PreToolUse rule engine for coding agents.

Probity is the second, required half of this distribution's install, not an add-on: the skills teach the disciplines, Probity enforces them on every tool call. The README's Quick Start ([Part 2](../README.md#part-2-install-and-configure-probity-in-the-target-project)) is the step-by-step install; this document is the reference behind it.

## Why

The skills in this catalog are prose: the agent reads the rules and follows them. That works until it doesn't — the Common Rationalizations tables exist precisely because prose gets rationalized away under pressure. Probity closes that gap: it intercepts every `Write`/`Edit`/`Bash` call *before it executes*, validates it against configured rules, and blocks violations with a corrective message the agent self-corrects from. The skills keep teaching the *why and how*; Probity enforces the *that*, per tool call.

The two layers are complementary by design: when Probity blocks an action, its reason lands on an agent that has the corresponding skill in context, so the recovery is informed rather than blind.

## What's in the template

The rules ship as the [`@jjchill/probity-rules`](https://www.npmjs.com/package/@jjchill/probity-rules) npm package — presets under `presets/`, custom rule modules under `rules/` — and the `probity.config*.ts` files in this directory are the thin consumer templates that import from it. Language-neutral gate rules live in [`probity/rules/gates.ts`](probity/rules/gates.ts) — they take every language-shaped decision (test-command shape, ambient-call shape) as a pattern option, and the Kotlin preset re-exports them with JVM/Gradle defaults:

| Rule | Skill it enforces | Mechanism |
|---|---|---|
| `enforceTdd()` (Probity built-in; `enforceJsTdd()` in the JS preset, `enforceKotlinTdd()` in the Kotlin presets) | test-driven-development | AI-validated: every production write must address an observed failing test, minimally; refactor debts block the next red |
| `forbidContentPattern(KNOWN_INFRASTRUCTURE_IMPORTS)` | ports-and-adapters | Deterministic: known framework/vendor/OS-I/O imports never enter core code — caught free, before any AI call |
| `enforcePortsBoundary()` (custom) | ports-and-adapters | AI-validated: the Dependency Rule, thin adapters (no business conditionals), vendor types kept out of port signatures |
| `enforceAdapterObservability()` (custom) | ports-and-adapters + observability-and-instrumentation | AI-validated, scoped to adapter paths: a NEW adapter path doing external I/O must carry boundary observability — a structured event, a port-tap/recording decorator, or a span. Thin, not blind. Delta-based; pure mappers, wiring, and tests pass; takes a `conventionHint` naming your telemetry convention. Guarantees telemetry *presence*, never field safety (sensitive-field discipline stays with review). Note it runs after the TDD gate (first violation wins), so on brand-new behaviour TDD answers first — a second-pass gate; its deny text tells the agent to assert the event in the failing test so both gates ask for the same thing, and `withTelemetryFastPath` makes telemetry-only additions free on both sides |
| `enforceThinDrivingAdapter()` + `forbidNewDomainDiscriminantChecks()` (custom, JS, Kotlin & KMP presets) | ports-and-adapters + frontend-ui-engineering | The opposite direction from the core-purity rules: business logic must not leak *out* of the core into driving adapters (UI components, pages, route handlers). AI-validated, scoped by the JS preset's `drivingAdapterGlobs` (default `src/ui/**`, `src/components/**`, `src/**/*.tsx`, minus tests and stories; `[]` switches it off): blocks a write that adds a decision in domain terms, coordinates more than one port/use-case call, re-implements a rule the core exports, or files a framework-free use case under a UI path, and names the extraction target (domain function or use case). Rendering, display formatting, local view state, display conditions over the rows already shown (empty, single item, first or last row) unless they repeat a rule the core enforces, and one call per user intent pass. Delta-based. Runs before the TDD gate, which can't catch these (a component test makes the logic "tested"). `coreExportsInJudge: true` gives the judge `coreGlobs`' export names, so copies of existing rules are named. The deterministic screen is opt-in via `domainDiscriminants` (e.g. `['role', 'plan']`): net-new literal comparisons on those fields block free, before the AI call. No default list, since `status === 'loading'` is ordinary view state. In the Kotlin and KMP presets the block is **opt-in** (no `drivingAdapterGlobs` default; see the layout table below), the screen also matches enum entries, `when (x.role)` subjects and `is` checks, the judge gets a Kotlin addendum for CLI commands and Compose screens, and `coreApiPaths` reads binary-compatibility-validator dumps for a repo with no core source |
| `forbidInternalModuleMocks()` (custom) | ports-and-adapters | Deterministic: blocks newly introduced `jest.mock()` / `vi.mock()` of the team's own modules — "Ports Are the Only Test Seam". Pre-existing mocks don't re-trigger, so suites migrate incrementally |
| `enforceLayeredImports()` (custom, opt-in) | ports-and-adapters + frontend-ui-engineering | Deterministic, delta-based: an ordered set of layers (atomic design levels, presentation over data), lowest first. Blocks a write that adds a reference from a layer to one above it, or to a sibling at the same rank. Kotlin: `import` lines and fully-qualified references; Swift: `import` lines. `strict: true` allows only the layer directly below. See [Layered imports](#layered-imports-enforcelayeredimports). |
| `enforceAcceptanceLanguage()` (custom) | acceptance-testing (+ ubiquitous-language) | AI-validated: the Language Test on spec-layer files — no UI/protocol/persistence mechanics, single outcome per spec, glossary terms verbatim when `glossaryPath` is set. One standard across artifacts: wording that violates in a test step ("the backend rejects creation") violates in the Markdown scenario too — the spec is judged as the source tests transcribe. With `specsDir` (wired by every preset), the judge is shown which of the write's new steps other specifications already use word for word, as settled wording it does not block on, so a step gets the same verdict in every feature file. The glossary is included up to 32,000 characters (`maxGlossaryChars`); beyond that the judge is told the rest is not shown |
| `requireSpecBackedAcceptanceTest()` (custom, Kotlin & Swift presets) | acceptance-testing + specification-by-example | Deterministic, write-time: a write adding a new acceptance test case must also add a `Covers:` tag resolving to a scenario that already exists in `docs/specs` — the feature file is written before the test that claims it. Closes the tagless-suite gap the commit-time parity gate can't see |
| `requireGreenTestRun()` (custom, `gates.ts` — all configs) | test-driven-development / `/build` / `/ship` | Deterministic: `git commit` is blocked unless the test suite ran after the last write **and its recorded output was green** — Probity's `requireCommand` checks only that a run was recorded, and would pass a transcript whose latest run failed. The language-neutral gate takes a command regex plus success/failure patterns, with two additive options — `commandPredicate` (narrows which regex-matched commands count) and `extraSuccessPredicate`/`extraFailurePredicate` (command-aware signals alongside the text patterns) — unused by default. The Kotlin preset layers Gradle-specific defaults on these hooks, applied only when the caller passes its exported `GRADLE_TEST_COMMAND` unchanged: accepted tasks are `test`/flavored or module-qualified `test...Test`, `allTests`, `jvmTest`, `build`, and `check`, recognized inside piped/compound strings while rejecting `--dry-run`, `-x`/`--exclude-task`, flag/redirect-value spoofing, and non-running lookalike tasks. A run is green via Gradle's `BUILD SUCCESSFUL` banner, or — under Kiro, only when the final simple command is itself a Gradle verification invocation — a structured tool-result `exit_status` of zero; any other regex, or Swift's own `xcodebuild` command, gets none of this. The JS preset's default command counts a run only when one of its top-level commands starts the suite (`npm`/`pnpm`/`yarn`/`bun` `test` or `run test[:…]`, or `vitest`/`jest`, directly or through `npx`), via the exported `isJsTestInvocation` (from 0.4.58; #150), so `echo vitest` or an issue body that mentions jest is not a run. A custom `commitCommand` is used as given, so anchor it. A run with no failure but no summary line (output cut by `| grep`/`| head`/`| tail`) gets its own deny naming the summary pattern (from 0.4.57; #162). `options.reason` appends on either deny path. A red-run deny ends with `Judged run:` and the command it judged (from 0.4.46; #138), so a surprising deny shows which recorded invocation was taken as the last run. An optional `enforceForPaths` scopes the demand to commits touching matching files. With several worktrees of one repository in a session (from 0.4.53; #152), the gate judges only the commit's own worktree: a write whose path lies in another worktree, and a run that starts with `cd <absolute path>` into another worktree, are left out. A run with no leading `cd`, or a relative one, still counts for every worktree, since the transcript doesn't record where it ran. Same inherent limit: runs outside the session transcript (another terminal, CI) are invisible |
| `forbidNewAmbientEffects()` (custom, `gates.ts` — all configs) | ports-and-adapters | Deterministic, delta-based: net-new direct clock/randomness/environment reads in core code are blocked (`JS_AMBIENT_EFFECT_PATTERNS` covers `Date.now()`, argless `new Date()`, `Math.random()`, `randomUUID()`, `process.env`; the Kotlin re-export covers the JVM equivalents). Clock, randomness, and config are ports; a `seamHint` names your canonical one. Existing brownfield call sites don't block — only what a write introduces |
| `surfaceRemovedStringUsage()` (custom, `gates.ts`) | frontend-ui-engineering × acceptance-testing | Deterministic, delta-based: a UI-code write that removes a string literal still referenced verbatim by E2E/smoke specs (which select by visible text or accessible name, and typically don't run in the quick local loop) is blocked with the list of dependent spec files — the "renamed a button, broke the deploy gate" failure caught at write time instead of in CI |
| `withMutationProbe()` + `enforceProbeReversion()` (custom, Kotlin & Swift presets) | acceptance-testing (mutation checks) | Deterministic pair: a production write marked `// probity: mutation-probe` (a deliberate break proving a retrofitted test bites) bypasses the TDD gate, and `git commit` is blocked while any probe marker is still on disk — an enforced mark → red → revert → commit round-trip instead of an override. The marker works on any file the TDD block covers, including a test-support stub or fake that lives in a `src/main` source set (it is judged as production code), and an unmarked write denied for lacking a red gets a deny-text note naming the marker |
| `enforceControlledPreconditions()` (custom) | acceptance-testing (controlled preconditions) | AI-validated, scoped to the driver and test-control layers (the opposite scoping from `enforceAcceptanceLanguage`): a driver method named for a precondition must establish it (fixture key, launch environment, programmed fake), and control wiring is never deleted just because the scenario passes without it — see "Brownfield seam gaps" below |
| `withInverseScenarioGuidance()` (custom) | test-driven-development × acceptance-testing | Deterministic wrapper over the TDD gate: verdicts unchanged, but a violation on the test-control layer (acceptance composition root, fixtures) gains the guidance that applies — the inverse-scenario escape route on missing-red/content-removing denials (so "observe a red first" never reads as "delete the control"), or an atomic-fixture hint on undefined-symbol denials (a fake + its fixture key + its enum value are one unit, landed piecewise). Other denials pass through untouched |
| `withCharacterizationTest()` + `enforceCharacterizationResolution()` (custom, Kotlin, KMP & Swift presets) | test-driven-development × acceptance-testing (characterization coverage) | Deterministic pair sanctioning the FIRST test for pre-existing behavior (born green — no red can precede it): a test-layer write marked `// probity: characterization` bypasses the TDD gate; the marker only comes off through a proof-checked removal (the transcript must record that test failing under a mutation probe), and `git commit` is blocked while any marker is on disk — an enforced write → probe → red → revert → prove → commit round-trip. An unmarked test-layer write denied for lacking a red gets a deny-text note naming the marker, so an agent pinning existing behavior (e.g. a branch a mutation review found untested) finds the sanctioned route instead of breaking production to manufacture a red. A test-layer write denied as retrofitting a red test to the code gets a restart-the-cycle note instead (revert the production change and the test, rewrite the test with the corrected expectation, watch it fail, reapply), and neither marker is offered |
| `withJudgeFailureDiagnostics()` (custom, `gates.ts` — TDD judge in all presets) | test-driven-development | Deterministic wrapper over an AI-validated rule: when the judge returns no verdict (a spend-limit or auth notice, empty or non-JSON output), the write stays blocked, but the deny text says it was NOT judged, names the judge, says whether the provider reported itself unavailable, and lists the writes that never call the judge — instead of Probity's raw `could not parse verdict from validator output: …`, which reads like a policy rejection and sends agents into futile rewording retries. Genuine verdicts pass through untouched |

### Driving adapters by project layout

Where the driving adapters live, and where the judge learns what the core already exports, depends on the layout. The JS preset wires the block by default because React apps usually keep UI and domain together. The Kotlin, KMP and Swift presets wire it only when `drivingAdapterGlobs` is set: a core-only repo has no UI, and a default glob there would only show up as a `DEAD SCOPE` in `probity-scope-report`.

| Layout | Example | `drivingAdapterGlobs` to start from | Core exports for the judge |
|---|---|---|---|
| UI with the core | a React app; a KMP app with `composeApp/` | JS: the default. KMP: `['**/composeApp/src/**', '**/src/*Main/**/ui/**', '!**/*Preview*.kt']` | `coreExportsInJudge: true` (reads `coreGlobs` source) |
| Core-only SDK with a CLI | mysudo-core | `['cli/src/main/**/commands/**']` (leave out the composition root and config adapters) | `coreExportsInJudge: true` |
| UI-only app on a core SDK | an Android app depending on the SDK as a library | the app's `ui/` packages | `coreApiPaths: ['path/to/sdk/api']`, the SDK's `.api`/`.klib.api` dumps |
| SwiftUI with the core (one app, or core and UI targets in one repo) | an iOS app with `App/Sources/Modules/*` | `['App/Sources/**/Views/**', 'App/Sources/**/*View.swift', 'App/Sources/**/*Screen.swift', '!**/*Tests.swift', '!AcceptanceTests/**', '!**/Previews/**']` | `coreExportsInJudge: true` (reads `coreGlobs` Swift source, views left out) |
| SwiftUI app on a core package or framework | an iOS app depending on the SDK as a Swift package or XCFramework | the app's view layer | `coreApiPaths: ['path/to/Core.xcframework']`, its `.swiftinterface` files (`.private` and `.package` ones are skipped) |

In the Swift preset, a view inside `coreGlobs` (a module folder holding both views and view models) moves to the driving-adapter judge and out of the ports-boundary judge, so a view write costs one AI call there, not two. View models (`ObservableObject`, `@Observable`) are presenters and stay with the core: the view sends them one intent per user action. `domainDiscriminants` in Swift matches enum cases as well as literals: `viewer.role == .superUser` in either order, `switch viewer.role`, and `if case .draft = timesheet.status`.

## Language presets

The config above is tuned for a JS/TS project. Probity's engine and the AI-validated rules are language-agnostic (they judge writes, not test runners), but the deterministic screens are ecosystem-specific, so per-language presets swap that layer:

- **JS / TS** — [`probity/probity.config.ts`](probity/probity.config.ts) + [`probity/presets/js.ts`](probity/presets/js.ts) (`jsRuleEntries`, `JsPresetOptions`). Spec-to-test traceability (the same mechanism documented under "Spec↔test traceability (KMP preset)" below) is OFF by default here — no behavior change until you set `options.specsDir` (an absolute path). Setting it wires `requireSpecBackedAcceptanceTest` on `acceptanceTestGlobs` (deterministic, ordered before the AI-validated TDD/Language Test rules), `surfaceScenarioLinkBreakage` on `specGlobs`, `enforceSpecTestParity` as a commit gate, and — once `glossaryPath` is also set — `surfaceGlossaryTermBreakage` on it. The write-time gate's `testDeclarationPattern` defaults to the exported `JS_TEST_DECLARATION` (see above), so it recognizes vitest/jest/mocha test cases out of the box; `testRoots` defaults to `[process.cwd()]` (Probity hook processes are anchored to the project root) `parityBaselinePath` plumbs the commit gate's incremental-adoption baseline, and `parityExclusionsPath`/`ignoreTags` configure a shared spec repository (see "Shared spec repositories" below).

- **Kotlin / JVM / Android** — [`probity/probity.config.kotlin.ts`](probity/probity.config.kotlin.ts) + [`probity/rules/kotlin.ts`](probity/rules/kotlin.ts). Replaces the ESM import screen with a Kotlin `import` screen (AWS, Amplify, Apollo, Firebase, OkHttp, Retrofit, Room, JDBC, Ktor, Spring, …); replaces the jest/vi mock blocker with `forbidStaticMocks()` (Mockito `mockStatic`, MockK's `mockkStatic`/`mockkObject`/`mockkConstructor`, PowerMock — the JVM's monkey-patching equivalents, which are always seam violations; plain `mock<T>()` is left to the AI rule since only it can tell a port from an internal class); adds `forbidNewAmbientEffects()` blocking net-new `Instant.now()` / `System.currentTimeMillis()` / `Date()` / `UUID.randomUUID()` / `Random()` / `System.getenv` in core code, with a `seamHint` pointing the agent at your canonical port; extends `enforcePortsBoundary` with a Kotlin/Android addendum (DI modules are composition roots, Robolectric-in-core-tests is a smell); and gates commits on Gradle verification tasks — see `requireGreenTestRun()` above for the accepted tasks, spoofing rejections, and Kiro exit-status allowance.

  Two config variants ship for Kotlin, differing in layout and test-double policy: [`probity.config.kotlin.ts`](probity/probity.config.kotlin.ts) targets a classic JVM/Android multi-module codebase (`src/main/java|kotlin`, `*-core`/`*-ui` module split, a mocking library present but its monkey-patching APIs blocked); [`probity.config.kmp.ts`](probity/probity.config.kmp.ts) targets Kotlin Multiplatform with per-feature hexagonal packages (KMP source-set globs like `src/*Main/kotlin`, core purity scoped to `domain`/`port`/`usecase`/`presentation` packages with Koin included in the core import screen, a no-mocking-library-at-all rule for fakes-only conventions via `MOCKING_LIBRARY_IMPORTS`, and acceptance-language checks covering Markdown `*.feature.md` specs while excluding Robot DSL classes). The boundary-rule addendum also teaches the validator KMP idioms: `expect`/`actual` platform source sets are adapters, and a function-typed constructor parameter (`nowEpochMillis: () -> Long`) is a valid port — unless its default calls the real OS inside common code.

  `kmpRuleEntries(root, options?)`'s second parameter is `KmpPresetOptions` — a superset of the factory's original `{ driverScopes, defaultScopes }` shape, so existing callers passing that shape unchanged keep working. Every hardcoded path in the preset is now an overridable option, each defaulting to today's exact value: `specsDir` (`docs/specs`), `specGlobs` (`docs/specs/**/*.feature.md`), `glossaryPath` (`docs/GLOSSARY.md`), `coreGlobs`, `acceptanceTestGlobs` (`**/acceptance/**/*Spec.kt` / `*Test.kt`), `testRoots`, `testFilePattern`, `testDeclarationPattern`, `baselinePath`, plus `driverScopes`/`defaultScopes` as before. `kotlinRuleEntries`'s `KotlinPresetOptions` follows the same established style.

  Two Kotlin-specific notes. First, Probity's built-in single-new-test fast-path doesn't cover Kotlin, so the preset ships `withKotlinFastPath(enforceKotlinTdd())`: a write under a classic or KMP Kotlin test source set that adds exactly one runnable, structurally annotated `@Test` function passes deterministically (via ast-grep and the `tree-sitter-kotlin` grammar) instead of costing an AI call. An existing file must preserve every prior source byte and test function and make one contiguous insertion containing only the test (plus comments/whitespace) or a separate test class with no additional functions; a brand-new file may also include imports and property fixtures. The parser packages ship as exact-version optional dependencies and install automatically on supported platforms; `npm install --omit=optional` disables the deterministic path when required. Missing or failed parser support delegates to the AI judge with an explicit diagnostic. Test deletion, disabling or weakening, newly introduced disable controls, changes to existing test-container headers, declarations that shadow identifiers used by existing tests, multi-test writes, and all production-source paths always delegate. Like Probity's built-in fast paths, a deterministic pass skips the AI judge's green→red refactor-readiness check for that write. The delegated Kotlin judge retains 20 recent events (with each event clipped at 6,000 characters) so nearby Gradle reds survive normal source inspection while prompt growth stays bounded. Because of that clip, the judge cannot see most of a large file the session read, so the preset also wraps it in `withExtractionUnderGreen`: when a write creates a new production file and the latest Gradle build or test run was green, a separate judge gets the full on-disk content of the production files the session read or edited, and passes the write if every behavior in it is already there (an extract-and-move refactor, including an interface plus its implementation, with the original still in place). A move with new behavior added is blocked by name, since under green no failing test justifies it; an unsure answer falls through to the TDD judge. As an explicit Kotlin exception to the generic placeholder guidance, a targeted relevant test executing `TODO()`/`kotlin.NotImplementedError` is clean red without a second assertion-failure run; implementation remains bounded by assertions in the relevant test source visible in recent history. Compile/import/signature failures still authorize scaffolding only. One cohesive green write may span all methods or branches those visible assertions require, without artificial mid-write reruns. Git staging/index state is ignored. Second, the Kotlin deterministic rules are **delta-based** (they block only occurrences a write *introduces*), so a brownfield codebase with hundreds of existing direct clock calls migrates incrementally instead of having those files frozen.

  All three non-Swift presets (JS/TS, Kotlin, KMP) also screen the acceptance suite for new fixed waits with `forbidNewFixedWaits()` ([`probity/rules/gates.ts`](probity/rules/gates.ts)), the counterpart of the Swift preset's sleep screen below: `Thread.sleep`, `TimeUnit.*.sleep`, `SystemClock.sleep` and `delay(` for Kotlin (`KOTLIN_FIXED_WAIT_PATTERNS`); `waitForTimeout`, `setTimeout`, numeric `cy.wait`, `sleep(` and `browser.pause` for JS/TS (`JS_FIXED_WAIT_PATTERNS`). It covers the whole suite, the DSL and drivers included, through `fixedWaitGlobs` (default `['**/acceptance/**']`; `[]` turns it off). It is delta-based, so waits already in a file don't block edits to it, and waits named in comments don't count. `delay(` is screened even though under `runTest` it only moves virtual time: an acceptance test should advance its test clock or wait for the concluding event, not wait a set amount. Drivers wait through one poll-for-concluding-event helper; exempt that helper's file with a `!` glob in `fixedWaitGlobs`.

  Every preset can also judge the acceptance DSL for test isolation with `enforceTestIsolation()` ([`probity/rules/acceptance-language.ts`](probity/rules/acceptance-language.ts), issue #119). It denies an entity a test creates in a shared SUT reaching it without an alias, a stub keyed on the raw name instead of the aliased one, a write to a shared fixture, and clean-up of test data. Closing driver resources is fine, and a DSL that builds a fresh SUT per test passes the aliasing and clean-up checks. The judge sees the file's first 30 lines and the changed lines with a little context, never the whole file, and isn't called when a write adds no code. It is opt-in through `dslIsolationGlobs` (for example `['**/acceptance/dsl/**']`), because every DSL write that adds code costs a model call and in-process suites with a fresh SUT per test rarely need it. Turn it on when the suite runs against a SUT that outlives a test.

- **Swift / iOS** — [`probity/probity.config.swift.ts`](probity/probity.config.swift.ts) + [`probity/rules/swift.ts`](probity/rules/swift.ts). Most of the stack is reused verbatim because it is language-neutral: the spec-traceability rules already match Swift's `func test…` declarations, the language/glossary rules judge content, and the generic gates (`requireGreenTestRun`, the mutation-probe pair, `withTelemetryFastPath`) take patterns as options. The Swift module supplies only what is Xcode-specific: a fixed-sleep screen for the acceptance suite (`sleep`/`usleep`/`Thread.sleep`/`Task.sleep` — the top XCUITest flakiness source), an XCUITest-mechanics containment screen (`XCUIApplication`/`XCUIElement` allowed only in `AcceptanceTests/Drivers/`), and xcodebuild patterns for the commit gate (`xcodebuild … test` invocations judged green by the `** TEST SUCCEEDED **` banner or an `xcresulttool` summary reporting `"result": "Passed"`). One layout note: the parity scanners' default test-file pattern expects a lowercase `acceptance/` path segment; iOS suites conventionally live in `AcceptanceTests/`, so the preset overrides `testFilePattern` everywhere — keep that override if you rename the directory. Calibrated against a production CocoaPods + SwiftPM app with an XCUITest target plus an app-hosted component-test target sharing one scenario layer. The Swift preset also wires the brownfield seam-gap rules (see below): `enforceControlledPreconditions()` on `AcceptanceTests/Drivers/**` and the acceptance composition root, `withInverseScenarioGuidance()` around the TDD gate for writes to that root, and the characterization round-trip (`withCharacterizationTest()` on the acceptance suite plus the `enforceCharacterizationResolution()` commit gate).

## Excluding paths from every rule (`excludeGlobs`)

A `{ files, rules }` block's `files` list accepts `!`-prefixed globs as negations (picomatch's `ignore` option) alongside the includes — see [`probity/rules/scoping.ts`](probity/rules/scoping.ts). The KMP, Kotlin, and JS presets each take an `excludeGlobs` option (default `['spikes/**', '**/build/**']`) that appends `!`-negations for those globs to *every* files-scoped block the preset wires — so a throwaway spike or generated build output never gets claimed by the TDD gate, the boundary rules, or any other write-scoped rule, without hand-editing each block. It does not affect flat, non-files-scoped rules (the commit gates). Pass `excludeGlobs: []` to disable it and fall back to whatever your other globs already cover.

## Adapters only an app can exercise (`harnessGlobs`)

Some adapters can't be tested in a plain test process. The iOS Keychain, for one, refuses an unsigned Kotlin/Native simulator test (errSecNotAvailable), so a Keychain adapter's real behavior only shows inside a signed app. A project then runs a shared contract in a device harness app, which logs the names of the checks that fail ([#94](https://github.com/JJChill/agent-skills/issues/94)). From 0.4.24 the KMP and Kotlin presets support that loop:

- **`harnessGlobs`** (e.g. `['harness/**']`) takes the harness's own code out of the TDD block. A check-runner that can only run in the app could never be green under the TDD gate, because its Gradle test reaches only the failure path. The paths stay under every other block: core boundary, adapter observability, the shell-write screen.
- **The TDD judge counts a harness run as a red.** When the session shows the app's output naming failing checks, and the checks' source, each named check is an observed failing test for the adapter it exercises, and authorizes the behavior it asserts. A Gradle test that can only reach the adapter's refusal path doesn't narrow that.
- **Boundary events are part of the minimum green.** The event the observability rule requires at each external call a red covers (one per call or outcome, static fields) goes in with that call's green, instead of needing a red of its own. Anything else the contract doesn't assert, such as an item's accessibility attribute, still needs its own red: write a harness check for it, run it in the app, then implement.

```ts
rules: kmpRuleEntries(ROOT, { harnessGlobs: ['harness/**'] }),
```

## Vendor adapters only a live session can exercise (`vendorAdapterGlobs`)

Some adapter code can't go red in any offline test. A vendor SDK such as Twilio Voice or Video calls `onConnected`, `onParticipantDisconnected` or a call invite's listener only during a live call, with a valid access token or a real push. Host tests reach the decisions behind the port with fakes, and device tests can reach the failure path (Twilio rejects a bad token), but the success callbacks never fire offline. The TDD gate can never authorize them ([#102](https://github.com/JJChill/agent-skills/issues/102)).

From 0.4.30 the KMP, Kotlin and Swift presets take `vendorAdapterGlobs`, off by default. The files it names leave the TDD block and are held to **`enforceForwardingOnlyAdapter`** instead, an AI judge for adapters that hold nothing worth testing:

- **Passes:** one-to-one forwarding of a vendor callback to a port method, and of a port call to the SDK (`leave()` → `room.disconnect()`). Also reading what the vendor objects hold and converting it to the port's types (ids, error codes, a plain enum mapping, the size of the room's participant list), holding and releasing the vendor objects the forwarding needs (invites keyed by call SID), listeners, wiring, and boundary telemetry.
- **Blocks:** a decision (a branch on state, a value or a vendor error code), state beyond the held vendor objects (counters, sets, timers), policy (retries, backoff, de-duplication, sequencing several calls), and computation the adapter works out itself. The deny says to move it behind the port, where a host test with a fake drives it red first.

Adapter observability and the shell-write screen still cover these files. Name only the vendor-facing files, and keep tests out:

```ts
rules: kmpRuleEntries(ROOT, { vendorAdapterGlobs: ['**/src/androidMain/kotlin/**/adapter/Twilio*.kt'] }),
```

If your project *can* get credentials into a session, a device test that runs against the real service is still the stronger evidence: its failing run is an ordinary red for the TDD gate, and the file needs no `vendorAdapterGlobs`.

## Review record (`requireReviewRecord`)

`requireGreenTestRun` proves the tests ran. Nothing proved a review ran ([#178](https://github.com/JJChill/agent-skills/issues/178)). From 0.4.63, a merge into a protected branch can be required to carry the review record from code-review-and-quality (Step 6): `Reviewed-by-agent:` trailers in the last paragraph of the merge message. The record lists every reviewer considered, with `(ran, N findings[, M fixed])` or `(skipped: <reason>)`.

Settings live in a named `review` export next to the default one, because Probity's `Config` only takes `rules` and `ai`:

```ts
import { probityConfig, requireReviewRecord, reviewConfig } from '@jjchill/probity-rules'

// One regex for "code a gate cares about", shared with requireGreenTestRun's enforceForPaths.
const CODE = /^(src|app)\//

export const review = reviewConfig({
  record: { enforceForPaths: CODE, protectedBranches: ['main'] },
})

export default probityConfig({
  rules: [...kotlinRuleEntries(ROOT), requireReviewRecord(review)],
})
```

- **The gate (PreToolUse).** It denies `git merge` into a protected branch when the merge brings in a file matching `enforceForPaths` and its `-m`/`-F` message has no valid record. It finds the merge after a `cd` and with `git -C`, and reads a `-m "$(cat <<'EOF' … EOF)"` heredoc. It also denies a merge that would fast-forward, because no commit would hold the record (use `--no-ff`). For `gh pr merge`, it reads `--body`/`--body-file` and checks the PR's base branch. If it can't list the merged files, it enforces anyway (fail safe).
- **Not gated:** `--squash`, `--no-commit`, `--abort`/`--continue`, and a merge hidden in `bash -c` or a script.
- **The CI backstop.** `npx probity-review-record --range <base>..HEAD` checks every first-parent merge in the range whose own diff touches `enforceForPaths`, and exits 1 naming each commit with a missing or malformed record. It is the only check that sees merges made outside an agent session (a web UI, a human at a shell). Set the base to the commit where you adopted the record, so earlier merges aren't judged. Pass `--all-first-parent` to check direct and squashed commits on the branch too. In GitHub Actions, check out full history (`fetch-depth: 0`), or the range won't resolve and the checker exits 2.

## Review routing (`probity-review-route`)

Which reviewers a change gets shouldn't depend on the agent's judgement ([#181](https://github.com/JJChill/agent-skills/issues/181)). The router maps a diff to the review agents it warrants, using routes in the `review` export, with no model calls:

```ts
export const review = reviewConfig({
  ignore: ['.claude/curator/**'],
  routes: [
    { agent: 'dependency-auditor', why: 'manifest changed', paths: ['**/build.gradle.kts', '**/package.json'] },
    { agent: 'silent-failure-hunter', why: 'error handling', added: /\b(catch|runCatching)\b|getOrNull/ },
    { agent: 'architecture-conformance-reviewer', why: 'test doubles', added: /\b(mockk|Mockito)\b/, lines: 'code' },
    { agent: 'architecture-conformance-reviewer', why: 'third-party import',
      added: /^\s*import /, notAdded: /^\s*import (myapp|kotlin|kotlinx\.coroutines)\./ },
    { agent: 'agent-skills:security-auditor', why: 'secrets', added: /(password|apiKey|bearer|jwt)\b/i },
  ],
  fallback: ['code-reviewer'],
  record: { enforceForPaths: CODE, requireRoutedAgents: true },
})
```

- **A route fires** when a changed file matches `paths`, or when an added line matches `added` and that same line doesn't match `notAdded`. `lines: 'prod'` (the default) greps code files outside `testPaths`. `lines: 'code'` includes test sources too.
- **Never grepped:** files matching `nonCode` (Markdown, text, YAML, JSON, TOML, lockfiles, images), binary files, and `ignore` globs. Ignored files are left out of routing entirely.
- **When nothing fires:** `fallback` runs if a production code file changed. A docs- or config-only diff runs nothing. `always` agents run on any change.
- **Agent names** keep their configured spelling (`agent-skills:security-auditor`). An agent is listed once, with every reason it fired.
- **Globs** in `paths` and `ignore` are relative to `root` (default: the repository root). Regex options are tested against repo-relative paths. Don't point `root` at an absolute path in one checkout: run from another worktree, nothing would match. The CLIs warn when `root` lies outside the repository they route.

`npx probity-review-route [--base <ref>] [--format text|json]` prints one `agent|why` line per agent, so it can replace a hand-written router hook. The base defaults to the merge-base with `origin/<mainBranch>`. The diff runs from the base to the working tree, plus the index and any untracked files that aren't gitignored. It reads only added lines, never the `+++ b/<path>` header, so a file name can't fire a content route.

With `record.requireRoutedAgents`, the merge gate routes what the merge brings in and denies a record that doesn't list each selected agent (ran, or skipped with a reason). A routing error denies (fail safe). In CI, pass `--routed-range ${{ github.event.before }}..HEAD` to `probity-review-record`, so only newly pushed merges are judged against today's routes. Re-routing old merges would fail every merge made before a route existed. An all-zero start (a new branch or a force push) skips the routed checks.

## Review obligations (TDD exemptions that name a reviewer)

Projects carve files out of TDD where no harness can drive them red, such as `!**/*Screen.kt` for thin rendering. The carve-out is only safe while review keeps those files thin. Nothing tied the two together, and logic leaked into an exempt screen ([#181](https://github.com/JJChill/agent-skills/issues/181)). An exemption can now declare its obligation on the negation itself:

```ts
const rules = kotlinRuleEntries(ROOT, {
  tddGlobs: [
    'ui/web/src/**',
    {
      glob: '!ui/web/src/commonMain/**/*Screen.kt',
      id: 'thin-rendering',
      reviewWith: 'code-reviewer',
      check: 'no branching on domain state; only renders view-model fields',
      reason: 'screens are thin rendering; logic is unit-tested in the view model',
    },
  ],
})

export const review = reviewConfig({ record: { enforceForPaths: CODE, requireObligations: true } })

export default probityConfig({
  rules: [...rules, requireReviewRecord(review, { obligationsFrom: rules })],
})
```

- **Where it's accepted.** `tddGlobs` in the Kotlin, JS and Swift presets, and `tddExemptions` in the KMP preset, whose TDD globs are fixed. For hand-written blocks, use `reviewedBlock({ files: [...], rules })`. Other glob options take strings only.
- **What the block gets.** The plain `!` negation, so TDD scoping is unchanged. The obligation travels with the block as metadata.
- **Routing.** `probity-review-route` lists each obligation a diff incurs, with its files. It also routes the `reviewWith` agent, with the `check` as the reason. Obligations never suppress the fallback.
- **The record.** It must carry `Review-obligation: <id> (addressed by <agent>)`, and that agent must have run, not been skipped. With `requireObligations`, the merge gate denies otherwise, and so does `probity-review-record --routed-range` in CI.
- **Setup.** `probity-scope-report` lists each obligation with the number of files it covers. It warns (exit 1 under `--strict`) about a plain `!` in `tddGlobs` that declares no obligation.
- **Paths.** Obligation globs, like route globs, are matched relative to `review.root`, which defaults to the repository root. If `probity.config.ts` isn't at the root, set `root: ROOT`.

## Shell writes to scoped files (`shellWriteScreen`)

Probity's content rules judge write actions: `Write`, `Edit` and `NotebookEdit` in Claude Code, the write tool in Kiro. A file changed by a shell command (`sed -i`, `cat > file <<EOF`, `tee`, `cp`/`mv`, `git apply`, or a `python3 - <<'EOF' … open(p, 'w')` script) reaches Probity as a command, so none of those rules see it. Scripted edits are an ordinary shell idiom, which makes this an easy bypass to take by accident ([#79](https://github.com/JJChill/agent-skills/issues/79)).

From 0.4.21 every preset puts `forbidShellWritesToScopedFiles` ([`probity/rules/shell-writes.ts`](probity/rules/shell-writes.ts)) first. It reads each shell command for the files it writes and denies the command when one of them falls inside any files-scoped block the preset wires, `excludeGlobs` applied, telling the agent to make the change with the write tool. It is deterministic and costs no AI call. It covers Claude Code's `Bash` and Kiro's `shell` (through the Kiro shim) alike.

The commit gates (`requireGreenTestRun`, `enforceSpecTestParity`, `enforceProbeReversion`, `enforceCharacterizationResolution`) read commands with the same parser (`isGitCommit`, from 0.4.36; #121). A command is a commit when `git` runs with `commit` as its subcommand (any global options before it), or when the words reach something that might execute them: a shell, `eval`, `xargs`, `find -exec`, an interpreter, a pipeline into one, or a `$(…)`/backtick substitution the shell expands whose own command is a commit. The same words in data are not a commit: a quoted heredoc written to a file with `cat`, an `echo`, a `gh` or `glab` body, a `grep` pattern. From 0.4.46 (#138) that includes a body passed as `--body "$(cat <<'EOF' … EOF)"` and backticks inside single quotes, which the shell never runs; `"$(git commit …)"` and backticks inside double quotes still count. Commands not known to treat their input as data still count, so the gates fail closed.

It reads the command text and does not run it. It recognizes redirects (`>`, `>>`, `&>`, `tee`), `sed -i`, `perl -i`, `cp`/`mv`/`install`/`ln`/`rsync` destinations, `dd of=`, `truncate`, patches from `git apply` or `patch` (a heredoc or a patch file), and `python`/`node`/`ruby`/`perl`/`bun`/`deno`/`php` scripts given inline (`-c`, `-e`, a heredoc) that call a file-writing API. It follows shell variables, `for` loop variables and `cd` within the command, and resolves relative paths from the session's cwd when the hook passes it (`probity-claude` and the Kiro shim do). For such a script, any scoped path the command mentions counts, because the script can name its target through a variable or an argument. So a script that reads a scoped file and writes a report elsewhere is denied too; print the report to stdout instead. What it can't see still passes: a script file named on the command line (`python3 tool.py`), writes through `find -exec` or `xargs`, and paths computed at run time. Formatters (`prettier --write`, `ktlint -F`, `swiftformat`) and `git checkout`/`git restore` pass, as before.

Pass `shellWriteScreen: false` to a preset to switch it off. A config that adds its own `{ files, rules }` blocks next to a preset's should screen them too: build the list with the preset's screen off and wrap the whole list.

```ts
import { withShellWriteScreen } from '@jjchill/probity-rules'

rules: withShellWriteScreen(
  [...kmpRuleEntries(ROOT, { shellWriteScreen: false }), ...projectBlocks],
  { root: ROOT },
),
```

## Layered imports (`enforceLayeredImports`)

For code organised as ordered layers, where each layer may use only the layers below it: atomic design levels in a design system (tokens, atoms, molecules, organisms, templates), or presentation over domain over data. A test that scans the sources catches an upward import after the write; this rule refuses it at write time and names the layer order. No preset turns it on. Add a block for the layered code:

```ts
import { enforceLayeredImports } from '@jjchill/probity-rules'

const D = 'com.example.ui.design'
// in Config.rules, after the preset's entries:
{
  files: ['ui/design/src/**/*.kt', '!**/src/*Test/**'],
  rules: [
    enforceLayeredImports({
      layers: [
        { name: 'tokens', packages: [`${D}.tokens`] },
        { name: 'atoms', packages: [`${D}.atoms`] },
        { name: 'molecules', packages: [`${D}.molecules`] },
        { name: 'organisms', packages: [`${D}.organisms`] },
        { name: 'templates', packages: [`${D}.templates`] },
      ],
      hint: 'see ADR 0012',
    }),
  ],
}
```

- **Placing a reference.** `packages` are Kotlin package prefixes or Swift module names; the prefix matching the most segments wins. A Kotlin file is placed by its `package` line, a Swift file by the layer's `paths` globs. A reference or file in no layer is ignored.
- **What counts.** Kotlin: `import` lines and fully-qualified names in code. Swift: `import` lines, including `@testable import` and `import struct M.T`. Comments and string literals are skipped.
- **Siblings.** A nested array is a group at one rank (`[{ name: 'home', … }, { name: 'settings', … }]`): each may use lower ranks, not the others. A `*` segment does the same for packages nobody lists: `com.x.feature.*` makes `feature.home` and `feature.settings` siblings, while `feature.home.ui` may still use `feature.home`.
- **`strict: true`.** A layer may use only the rank directly below it.
- **Delta-based.** Only references the write adds block; an existing upward import doesn't freeze its file.

## Spec↔test traceability (KMP preset)

The KMP preset also enforces the `acceptance-testing` skill's definition of done mechanically: every scenario in a Markdown spec is claimed by an acceptance test, and every claim resolves to a real scenario. The link is declared, not inferred — a test carries a tag (comment or annotation argument):

```kotlin
// Covers: messaging.feature.md :: Scenario: Message is delivered to a contact
```

The rules accept both spec formats interchangeably: Markdown feature files (`<name>.feature.md`, `## Scenario:` headings, `(wip)`/`[scope]` markers) and real Gherkin (`<name>.feature`, `Scenario:` lines, `@wip`/`@scope` tags). `Covers:` tags resolve by spec *stem*, so a tag's extension need not match the spec's on disk — a suite can migrate one file at a time (or reference specs from a shared `.feature` repo, e.g. mounted as a `docs/specs` git submodule) with parity green throughout. A stem present in both extensions at once is rejected as an unfinished rename.

Three deterministic rules in [`probity/rules/spec-test-parity.ts`](probity/rules/spec-test-parity.ts) hold the invariant from both ends — and enforce the *ordering*:

- **`requireSpecBackedAcceptanceTest({ specsDir, testDeclarationPattern? })`** fires at write time on the acceptance test-case layer: a write that adds a new test case must also add a `Covers:` tag resolving to a scenario heading (`## Scenario:` or Gherkin `Scenario:`) that **already exists** in `specsDir`. This is spec-first made mechanical — an agent cannot author acceptance tests without writing the feature file first, and the deny message says exactly what to create and where. Delta-based: edits inside existing brownfield test files pass untouched, and `(wip)`/`(planned)` scenarios count as existing (they're exactly what outside-in work drives against). Without this rule, a tagless acceptance suite is invisible to the commit gate below — the gap we hit on a real iOS trial, where an agent produced a whole suite with no feature file and nothing objected. `testDeclarationPattern` controls what counts as a test-case declaration, defaulting to Kotlin/Java `@Test` or Swift `func test…`; the package also exports **`JS_TEST_DECLARATION`** (from `rules/spec-test-parity.ts`) for a JS/TS project — it matches vitest/jest/mocha `it(`/`test(` and their `.only`/`.skip`/`.each(...)( `/`.concurrent` variants, but never `describe(` or an identifier that merely ends in "it"/"test" (`split(`, `submit(`, `logger.audit(`). The JS preset (below) passes it by default once its own `specsDir` option turns parity on.

- **`enforceSpecTestParity()`** gates relevant `git commit` actions: before scanning, it reads the pending commit and proceeds only when that commit records the specs path (including a git-submodule pointer), the configured baseline file, or a configured acceptance-test path. It then scans `docs/specs/*.feature{,.md}` for scenarios (Markdown `## Scenario:` or Gherkin `Scenario:`) and the acceptance dirs for `Covers:` tags, and blocks with a two-sided report — scenarios no test claims, and tags pointing at scenarios that no longer exist. Git inspection failures retain full enforcement. This commit scoping is what makes a separate specs repository genuinely spec-first: its own commit can remove `@wip` before a covering test exists in the parent, while the later parent commit that records the submodule pointer or acceptance test still enforces parity. Parity requires the *link*, not a passing run (the claiming test may still be red or quarantined); scenarios still being driven outside-in are exempted with `## Scenario (wip):` (or a Gherkin `@wip` tag).

  **Brownfield adoption:** a spec suite that predates the gate would block every specs/acceptance commit (a real KMP app we trialed this on had 454 scenarios and zero tags). The rule takes a `baselinePath`: generate the baseline once — `npx probity-spec-parity --specs docs/specs --baseline docs/specs/.parity-baseline --write-baseline` — and commit it. Baselined scenarios are exempt from the orphan check while every new scenario is enforced from day one; burn the file down by deleting lines as coverage lands. A missing baseline file means full enforcement (the greenfield default), and dangling `Covers:` tags are never baselined — they are actively wrong, not legacy.

  **Per-scenario driver mapping:** the rule optionally checks coverage per *(scenario, driver scope)*, not just per scenario. Declare named scopes (`driverScopes: [{ name: 'system', filePattern: /AcceptanceTests[/\\]Specs[/\\]/ }, …]`) mapping each scope to its test files, and tag scenarios that need more than the default suite — `## Scenario [system]: …` (composes with wip as `## Scenario (wip) [system]:`). A tagged scenario must be covered by a test matching that scope's pattern, on top of the base check; `defaultScopes` names scopes every scenario must satisfy even untagged (the project's standard driver set). Declare an app scope whose driver builds the app through its shipping composition root with fakes only at outbound ports, and tag scenarios `[app]` by the `acceptance-testing` skill's tier rules: the wire, wiring or a platform service decides the outcome, a walking skeleton per feature that reaches an external system, and escaped defects. Everything else is claimed at the component tier (issue #118). Scopes stay opt-in: the presets set no `driverScopes`, so adopting this is a config change in the consuming project. Tags are floors, never ceilings — extra coverage in other scopes is always fine — and a tag naming an undeclared scope blocks (misspelling protection). Tags never change scenario keys, so existing `Covers:` tags and baselines are unaffected; baselined and wip scenarios are exempt from scope checks too. The rationale and the tag convention live in the `acceptance-testing` skill's Layer 3 section.

  **The baseline is where dead coverage hides.** While it exists, the parity gate is advisory for everything in it — and mutation checks are the mechanism that surfaces the cost: a mutation probe that stays green under every suite usually means the behavior's scenario is sitting in the baseline, untested. Treat every green probe as a burn-down prompt (write the claiming test, delete the baseline line), not as a reason to pick a different probe.
  **Shared spec repositories:** when several projects consume one spec repository (typically a `docs/specs` git submodule), not every scenario is every project's to automate — a backend-enforced rule, say, or SDK-internal behaviour an app built on that SDK doesn't re-cover. Each project lists those in its own **exclusions file** (`exclusionsPath`; the KMP and Swift presets default to `docs/spec-exclusions.txt`, the JS preset takes `parityExclusionsPath` with no default), one `<spec>.feature :: <title> # <reason>` per line. The reason is required and should name the owner (`# backend enforces the block list`, `# covered by mysudo-core-sdk 2.3`). Excluded scenarios skip the orphan and scope checks. Exclusions are standing decisions, not debt, so they never go in the baseline, and the gate keeps them honest: a malformed line, an exclusion matching no scenario, one for a scenario a test now claims, and one for a scenario still in the baseline all block. Precedence is claimed > excluded > wip > baseline, and `--write-baseline` leaves excluded scenarios out. Shared tags that are not driver scopes in this project go in **`ignoreTags`** (Gherkin `@tags` and Markdown `[tags]` alike); unknown tags not listed there still block, so misspelling protection stays, and a tag listed both as a scope and as ignored blocks as a contradiction. Work in progress is per project too (#111): shared `@wip` markers are controlled by whichever consumer touches the spec first, so a project lists its own in a **wip file** (`wipPath`; KMP and Swift default `docs/spec-wip.txt`, JS `parityWipPath` with no default; CLI `--wip`), same line format as exclusions with a required note on what is happening or what blocks it. `sharedWip: 'ignore'` (`--shared-wip ignore`) makes the specs' own markers informational so the wip file is the only list; the default `'honor'` keeps today's behaviour. Three files, three meanings: exclusions are standing ("never ours", with an owner), the baseline is a snapshot from adoption that only shrinks, and the wip file is "ours, not done yet". The gate keeps them apart: a wip line for a claimed scenario (promoted — delete the line), an excluded one, a baselined one, or none blocks. "The baseline only shrinks" is otherwise a convention, not enforced. Keep the exclusions file, the wip file and the baseline outside the shared tree — the KMP and Swift baseline default is inside `docs/specs`, so a submodule consumer should override it. A commit that changes only one of these files still runs the gate. Background: issues #105, #106 and #111.

  **Live-only coverage (#112):** some scenarios' outcomes are produced entirely by a service the project doesn't own (the backend refuses a blocked caller), so a fake can't signal them and only a live run can. A test that checks one live, opt-in and usually skipped in CI, still claims it, but that coverage is weaker than a test every build runs. `liveTestPattern` (CLI `--live <regex>`) marks live test files by path, like a driver scope's `filePattern`. Their claims keep counting as coverage, and the CLI reports the scenarios covered by live tests only as their own group (`… covered (2 by live tests only)`, then the list). The commit gate can't warn, so on its own the pattern changes nothing there. `liveFloorScopes` (CLI `--live-floor a,b`) adds a floor: a scenario tagged with one of those scopes needs a claim from a test that isn't live, and a scenario covered only by live tests blocks. Exclusions work as before: when a live test starts claiming an excluded scenario, the exclusion is stale and fails, and the project deletes it.

  **A dependency's coverage (#114):** an app built on an SDK that consumes the same specs shouldn't re-cover the SDK's internals (offline sync, how a key backup is sealed). An exclusion naming the SDK works, but nothing checks it. Instead, the SDK writes the scenarios it covers with `spec-parity.mjs --write-claims <file> --claims-source "<name> <version>"`: one line per scenario a finished test claims, pinned to a hash of the scenario's steps (`@id:offline-sync sha=1a2b3c4d5e6f`, or the title form). The app commits that file next to its exclusions and points `dependencyClaimsPaths` (CLI `--dependency-claims <file>`, repeatable) at it, updating the file on each SDK bump. A claim covers a scenario the app has no finished test for while the steps in the app's specs still hash the same. A reworded title keeps an id claim; changed steps void it, and the scenario is reported uncovered with a note naming the claim's source. A dependency claim meets `defaultScopes` but never a scope tagged on the scenario, so a user-facing floor still needs the app's own test. An exclusion or wip line for a dependency-covered scenario blocks as stale. Claims for scenarios the app's spec revision doesn't have are ignored, and the CLI lists dependency coverage with its source. Everything stays offline: the gate reads only the committed file, never a build cache or lockfile.

  **In-progress acceptance tests (#115):** a spec that drives a feature is committed with the code while it still fails, **expected-to-fail**: it runs on every build and passes only while its scenario fails, so `requireGreenTestRun` sees a green build and needs no exception, and the build goes red once the feature works. The markers are the framework's own (Jest `test.failing`, Vitest `test.fails`, Swift Testing `withKnownIssue`, XCTest `XCTExpectFailure`) and, for Kotlin, a project-owned `inProgress { }` helper (the acceptance-testing skill gives it; kotlin.test has no expected-failure support and no tags). The gate reads a `Covers:` tag as belonging to the test it sits on (the next declaration, when only comments and annotations come between) or inside; when that test carries the marker (`inProgressPattern`, CLI `--in-progress`; default `DEFAULT_IN_PROGRESS_PATTERN`), the claim is **in progress**. An in-progress claim is not coverage: a scenario claimed only by in-progress tests must be wip (`@wip`/`(wip)` or a wip-file line), or the gate blocks. A wip scenario a finished test claims is promoted, and the gate blocks until its wip marker or line goes (the spec's own marker counts only under `sharedWip: 'honor'`). Scope checks count only finished claims; dangling tags and the exclusion contradictions count all of them. The Kotlin, Swift and JS TDD judges are told the same: an expected-to-fail test's green run is no evidence and no red, adding a new one is allowed, removing the marker makes it an ordinary test, and adding the marker to an existing test disables it.

- **`surfaceScenarioLinkBreakage()`** fires on `*.feature` / `*.feature.md` writes: removing or renaming a scenario heading that tests still claim blocks immediately, listing the affected tests — so a rename updates its `Covers:` tags in the same change instead of rotting until commit time.
- **`enforceScenarioFidelity({ specsDir, testRoots?, testFilePattern? })`** ([`probity/rules/scenario-fidelity.ts`](probity/rules/scenario-fidelity.ts), issue #120) is the judged half of the link. The rules above prove a `Covers:` tag resolves; this one checks the test says what the scenario says. It sends each changed claimed test, read through its DSL, to the judge beside the scenario's text, and denies a different precondition, a different action, a different outcome, or an outcome the scenario doesn't state. On a spec write it does the same for each changed scenario that tests already claim. A scenario marked wip (`@wip`, `@planned`, `(wip)`) is not held to its claims (from 0.4.54; #155), so a step both sides gain lands in three writes: mark the scenario wip and add the step, update the claiming test (judged against the new text), then remove the marker, which judges every claim on the scenario again, a Gherkin tag line included. Before, each side was judged against the other's old text, so neither could go first. It calls the model only when a write changes a claim: a write with no changed claim, a claim that resolves to nothing (left to the parity rules), and a test whose body matches another test claiming the same scenario (a second driver running a shared body) all pass for free. A test that delegates to a shared scenario body in a sibling `*Scenarios.*` file is judged with that file. The KMP and Swift presets wire it on their acceptance tests and specs by default, and the JS preset does once `specsDir` is set; `scenarioFidelity: false` turns it off. Given `appScope` (the preset option, beside `driverScopes`), the same judge call also checks each changed claim's tier (#129): it reports an untagged scenario whose own text shows the wire, wiring or a platform service decides its outcome, and never reports a tagged one as over-tiered, since walking skeletons and escaped-defect scenarios are app-tier for reasons the text can't show.

Because scenario titles are link keys, renames must touch the claiming tests — that's the point, and the breakage rule turns it into a guided step. A scenario can instead carry a **stable id** — a Gherkin `@id:<slug>` tag, or `id:<slug>` in the Markdown bracket list (`## Scenario [system, id:<slug>]: …`) — and references can cite it: `// Covers: @id:<slug>`, a baseline line `@id:<slug>`, an exclusion line `@id:<slug> # <reason>`. Rewording the title then touches nothing else, which matters most when several projects consume one spec repository (#106). Ids are optional, written by the spec author, unique across `specsDir` and one per scenario (both checked at commit, and by the CLI); an id is never a driver scope. Title references keep working, so a suite migrates one reference at a time. The breakage rule passes a title change claimed only by id, blocks dropping an id tests still cite, and — given `specsDir`, as the presets pass — lets an id move to another spec file. Retired ids are not tracked, so don't reuse one. Hooks only run in agent sessions, so the same check ships as a zero-dependency CLI for CI and human commits too, exposed as the package's `probity-spec-parity` bin: `npx probity-spec-parity --specs docs/specs` (exit 1 on breakage); driver scopes mirror as `--scope system=<path regex>` (repeatable) and `--default-scopes a,b`, and shared-repository settings as `--exclusions <file>`, `--ignore-tags a,b`, `--wip <file>` and `--shared-wip honor|ignore`. The CLI also checks the `acceptance-testing` skill's walking-skeleton tier rule (#129): `--app-scope app` (a declared scope) lists feature files with scenarios needing proof but no finished claim at that scope. It is a warning by default, because the commit gate has no warning channel and not every feature file reaches an external system; `--strict-skeleton` makes it fail in CI. Feature files that reach no external system go in a `--skeleton-exempt <file>`, one `<spec>.feature # <reason>` per line, and a line for a feature with an app-scope claim, or for no feature, is reported as stale.

## Brownfield seam gaps: preconditions are controlled, not observed

A failure mode from a real iOS trial, worth designing against. The scenario was "new user whose sign-in fails is told, and offered support." In the simulator the real sign-in path genuinely fails (no reachable backend), so the test went green **without** the control fixture the agent had written — and the TDD gate, correctly demanding a red before fixture code, appeared to "refuse" the fixture. The agent resolved the tension in the wrong direction: it deleted the fixture and let the environment own the scenario's Given. Two real costs follow: the test can't distinguish the failure it asked for from the failure the machine produced (on a connected machine the precondition silently inverts), and the *success* path becomes unspecifiable — nothing can make sign-in succeed until the port is controlled.

The principle (now in the `acceptance-testing` skill's Test Isolation section): **every Given is established by the test — fixture, programmed stub, substituted port — never inherited from the environment.** And the escape route when a control fixture can't get a red: the legitimate red is the **inverse scenario** on the same port ("a new user who signs in successfully is taken into the app"), which genuinely fails until the port is controllable; its red drives the fixture, and the original scenario then adopts the explicit fixture as a refactor under green.

Three pieces enforce this mechanically:

- **`enforceControlledPreconditions()`** ([`probity/rules/acceptance-language.ts`](probity/rules/acceptance-language.ts)) — AI-validated, scoped to protocol drivers and the acceptance composition root. Blocks the *no-op precondition driver* (a method named "…WhoseSignInWillFail" whose body only navigates and asserts, setting no fixture/stub/launch state — especially with a comment admitting the environment covers it) and blocks deleting control wiring on the grounds that the scenario is green without it, naming the inverse-scenario route in the deny text. Scope it to the layers `enforceAcceptanceLanguage` excludes (e.g. `AcceptanceTests/Drivers/**` plus the acceptance assembly).
- **`withInverseScenarioGuidance()`** ([`probity/rules/kotlin.ts`](probity/rules/kotlin.ts)) — wraps the TDD gate; on test-control paths its deny text gains the escape route, because the deny message is what the agent actually reads at the decision point.
- **The characterization round-trip** — the sibling trap, hit on the same trial: the behavior already exists in production, so its *first* test is born green and no red keyed to it can ever be observed — and a mutation probe can't help yet, because a probe only fails tests that already exist. An unwrapped TDD gate correctly denies the test write, leaving only an override or an unspecified behavior. `withCharacterizationTest()` + `enforceCharacterizationResolution()` ([`probity/rules/kotlin.ts`](probity/rules/kotlin.ts)) sanction it as an enforced round-trip instead: the test lands carrying `// probity: characterization` (test-layer paths only — production writes can't borrow the marker); the marker's removal is blocked until the session transcript records that test failing under a mutation probe (the acceptance-testing skill's mutation-check for retrofitted specs, made mechanical); and commits are blocked while any marker remains. The green is earned, not exempted.
- **Verdict-before-reasoning (a validator bug class, not a brownfield trap).** The same trial surfaced a denial whose reason text literally concluded "…Re-evaluating: this is minimal green for the observed failing test. Passing." — returned as a violation. Root cause: the validator response shape put `kind` before `reason`, and an autoregressive model emits fields in order — it must commit to the verdict before writing its analysis, so a mind changed mid-`reason` can't revise the already-emitted `kind`. The custom rules in this repo now use a reason-first shape (`{"reason":…,"kind":…}` — conclude, then label). Probity's built-in `enforceTdd` ships the kind-first shape and its response format is not configurable; until upstream fixes it, patch the installed package (the calibration projects carry a `patch-package` patch reordering the fields).
- **The stop-and-ask protocol** — when a scenario cannot be honestly driven at all because the seam itself is missing (no port to substitute, no composition root to substitute it in), the sanctioned move is to mark it `## Scenario (wip):` (which the parity gate already exempts) — or, when the specs are a shared repository, add a line to the project's wip file naming the missing seam (see "Shared spec repositories") — and surface the seam gap to the user as a design decision. Silently reshaping the scenario, weakening its Given, or letting the environment stand in is never the agent's call to make unilaterally.

## Ubiquitous language

The glossary (`docs/GLOSSARY.md`, format in [`probity/GLOSSARY.template.md`](probity/GLOSSARY.template.md): one term per `##` heading, one term per concept) is wired into both Kotlin config templates and enforced from three directions:

- **Usage in specs** — `enforceAcceptanceLanguage({ glossaryPath })`: spec content naming a recorded concept with a synonym or conflicting term is blocked. Optional strict mode `requireGlossaryEntry: true` enforces "the glossary conversation happens first": a domain concept with *no* entry blocks until the glossary gets one — turn it on once the glossary has real coverage, not day one.
- **Usage in code** — `enforcePortsBoundary({ glossaryPath })`: the boundary validator gets the glossary, so ports and domain types naming a recorded concept with a conflicting term are violations (`ShipmentStore` when the glossary says Parcel).
- **Drift** — `surfaceGlossaryTermBreakage()` on glossary writes: removing or renaming a term that specs, tests, or code still use blocks the edit with the list of users. Multi-word terms are matched as identifiers too (`Delivery Window` → `DeliveryWindow`/`deliveryWindow`/`delivery_window`). Retiring a term nothing uses passes silently.

All three degrade gracefully while `docs/GLOSSARY.md` doesn't exist, so the wiring costs nothing before the glossary conversation starts.

## Setup

Probity lives in the **consuming project** (the codebase you're building), not in this repo.

1. In your project, install Probity and the rule package (until `@jjchill/probity-rules` is published, install it from a local clone of this repo instead — see the README's Quick Start Part 2 for the exact command and the `npm run build` step it needs first):

   ```bash
   npm install -D @nizos/probity @jjchill/probity-rules
   ```

2. Copy the thin config template for your preset to your project root — this is the only file that needs copying; the rule modules and scripts it imports live inside the installed package:

   ```bash
   cp node_modules/@jjchill/probity-rules/probity.config.ts .
   ```

   (or `probity.config.kotlin.ts` / `.kmp.ts` / `.swift.ts`, matching the project's language.)

3. **Edit the preset's options.** The template calls a preset factory (`jsRuleEntries`, `kotlinRuleEntries`, `kmpRuleEntries`, or `swiftRuleEntries`) with an options object — that object is what you edit, not the package internals. The defaults assume a `src/core` + `src/adapters` layout; point the core-purity option at your actual core/domain code, the spec option at your actual spec layer, and the commit-gate option at your real test command. Wrong scoping is the main failure mode, in both directions: `enforcePortsBoundary` on adapter files or `enforceAcceptanceLanguage` on protocol drivers will block work those files are supposed to do (both rules instruct the validator to pass on clearly mis-scoped files, but don't rely on that), while a glob slightly too narrow for your layout fails silently — the rule simply never fires.

4. **Check the scoping** before the first agent session finds out the hard way, via the package's `probity-scope-report` bin:

   ```bash
   npx probity-scope-report --config probity.config.ts
   ```

   The report resolves every `{ files, rules }` block against your real tree with Probity's own glob semantics and prints what each block claims, flagging dead scopes (globs matching zero files — the silent failure), core-purity rules claiming adapter/DI/UI-looking production paths (test files are skipped — a test-wide screen such as a no-mocking-library rule legitimately covers adapter tests), and the acceptance-language rule claiming Robot/driver files. Re-run it (or wire `--strict` into CI) whenever the layout or the globs change. On a greenfield repository every layer starts empty, so pass `--allow-empty <glob>` (repeatable, an exact glob from the block's `files`) for layers that don't exist yet — CI can then run `--strict` from the first commit; drop each flag once its first file lands (the report notes stale ones).

   Relative globs are anchored at the config file's directory, as Probity anchors them. The report prints that directory. If the config sits outside `--root` (a scratch copy, or a monorepo keeping configs elsewhere), the report warns `CONFIG OUTSIDE ROOT`: relative include globs match nothing in the repo, and relative `!` exclusions (such as `excludeGlobs`' `spikes/**`) exclude nothing. That's also how enforcement behaves, so keep the config at the repo root, or write globs as `**/…` patterns ([#186](https://github.com/JJChill/agent-skills/issues/186)).

5. Wire the hook. Easiest is the plugin:

   ```
   /plugin marketplace add nizos/probity
   /plugin install probity@probity
   ```

   The plugin runs Probity's bare `probity` bin, which cannot see work done inside Claude Code sub-agents (see `probity-claude` below). If agents in this project use sub-agents, prefer the manual hook.

   Or manually in `.claude/settings.json`:

   ```json
   {
     "hooks": {
       "PreToolUse": [
         {
           "matcher": "Bash|Write|Edit|NotebookEdit",
           "hooks": [
             { "type": "command", "command": "cd \"$CLAUDE_PROJECT_DIR\" && ./node_modules/.bin/probity-claude" }
           ]
         }
       ]
     }
   }
   ```

   Use the package's `probity-claude` bin rather than Probity's own `probity` bin. When a Claude Code sub-agent (the Agent tool, including `isolation: "worktree"` agents) calls a tool, the hook payload carries the *parent* session's `transcript_path` plus an `agent_id`, and the sub-agent's own tool calls are recorded only in `<session>/subagents/agent-<agent_id>.jsonl`. The bare bin therefore judges sub-agent writes against the parent's history: the TDD judge never sees the sub-agent's red runs, and a characterization marker can never be released. `probity-claude` points `transcript_path` at the sub-agent's transcript when there is one, then runs Probity unchanged (it adds `--agent claude-code` itself). It also keeps long sessions working: Probity refuses a transcript over 100 MiB, so when the transcript passes that size, `probity-claude` hands Probity a private copy of its newest 32 MiB instead. Without the wrapper, every history-based rule denies from then on until a new session starts. From 0.4.46 (#138) it also drops Claude Code's `api-request-blob` transcript entries. Each one records a tool call a second time, after its result. Probity reads it as a second call with no output, so every test run had an empty copy after it. `requireGreenTestRun` judged that copy as the last run and denied every commit, and the TDD judge saw each run twice. The bare `probity` bin still reads those entries. And it runs Probity in the right tree: `$CLAUDE_PROJECT_DIR` keeps naming the main checkout after a session enters a worktree, so when the edited file (or a command's directory) is inside a git worktree nested in the project that has its own `probity.config.*`, `probity-claude` starts Probity there, and the rules judge that worktree's specs and files. The same holds for a worktree beside the project (`git worktree add ../<name>`), which `probity-claude` finds through `git worktree list`. Such a worktree usually has no `node_modules`, so its config loads the main checkout's packages: `probity-claude` adds that `node_modules` to `NODE_PATH`, which Node consults only after the worktree's own. Before 0.4.22 a sibling worktree stayed on the main checkout's config, whose rules don't cover paths outside it, so its calls went through unjudged. If the packages resolve nowhere, every call is denied with "Run npm ci in <tree>", except that install command itself. A Bash call keeps the session's cwd, so it often reaches another worktree by path (`sed -i … ../<name>/src/A.kt` from the main checkout). From 0.4.23 `probity-claude` reads the files a command writes, with the shell-write screen's own parser, and also runs Probity in each other worktree they lie in; the first deny stands. It passes the session's cwd to the screen as `PROBITY_SESSION_CWD`, so relative paths in a command resolve from where the command runs. Finally, it keeps a broken config fixable. Probity loads `probity.config.*` on every call and blocks every call when the load throws, including the edit that would fix the config: a config edited in two steps, a call before its import, locks the agent out until a human reverts the file. So for an Edit or Write to the config Probity would load, `probity-claude` loads the after-state first, from a scratch copy beside the config, and blocks the edit if it would not load. If the config already fails to load, edits to it are not blocked (the normal permission flow decides), and every other deny says which file to fix.

   Anchor the hook with `cd "$CLAUDE_PROJECT_DIR" &&`, never a bare relative `./node_modules/...`: hooks are not guaranteed to run with the repo root as their working directory (a session launched from a parent directory, a worktree, a `cd` elsewhere). A bare relative path then fails to resolve and the hook errors **non-blocking** — every rule silently stops enforcing while work continues. The `cd` also matters beyond binary resolution: Probity discovers `probity.config.ts` by searching upward from the working directory, so a hook run from the wrong cwd finds no config even with an absolute bin path. **Open Claude Code on the repository itself.** The hook lives in the repository's `.claude/settings.json`, and Probity finds `probity.config.ts` by searching upward from `$CLAUDE_PROJECT_DIR` — so a session opened on a parent folder that holds several repositories loads neither, and enforces nothing without any error. The agent-skills plugin's SessionStart notice (`hooks/probity-notice.sh`, the only hook the plugin registers) warns when that is the situation, and prints nothing otherwise: a `probity.config.*` in a repository one or two levels below the project, but none at its root. Prefer the direct bin path over `npx @nizos/probity`: the hook runs on **every** matched tool call, and npx's resolution overhead is ~0.6-1.6s per call vs ~0.2s for the bin (measured on a warm cache). A truly resident validator process would cut the remaining startup too, but that's engine work — worth an upstream issue, not something the templates can provide.

### Choosing the AI judge

By default the judged rules (the TDD gate and the other AI rules) run on Probity's own judge: the Claude Agent SDK on the logged-in Claude account. When that account hits its spend limit, every judged write is blocked until the limit resets. To judge on kiro-cli instead, or to fall back from one to the other, set `ai` in `probity.config.ts`:

```ts
import { claudeJudge, judgeChain, kiroJudge } from '@jjchill/probity-rules'

export default defineConfig({
  rules: kmpRuleEntries(root),
  ai: judgeChain([kiroJudge(), claudeJudge()]),
})
```

- **`kiroJudge(options?)`** runs each verdict as one `kiro-cli chat --no-interactive` call, with the prompt on stdin. It defaults to `claude-opus-5.5` at `high` effort; at `medium` it let a production write with no failing test through 7 times in 25. It uses a judge-only Kiro agent, `probity-judge`, with no tools and no hooks, which it writes into its own working directory (`<tmpdir>/probity-kiro-judge`). So a judge run cannot edit files, run commands, or set off the Kiro shim's hook, and Kiro's saved sessions for judge runs stay out of your project. Kiro keeps one saved session per verdict there, so clear that directory now and then. When kiro-cli is missing, exits with an error, prints nothing, or takes longer than `timeoutMs` (default 60 s), the verdict is "Kiro judge unavailable". Options: `model`, `effort`, `agent` (only an agent with no tools and no hooks), `timeoutMs`, `command`, `cwd`.
- **`claudeJudge(options?)`** is Probity's Claude judge, for use in a chain or as `ai` on its own. From 0.4.49 it runs the Claude Code installed on the machine, not the copy bundled with Probity's Agent SDK: the binary running the current Claude Code session (`CLAUDE_CODE_EXECPATH`, which hooks inherit), else the first `claude` on `PATH`, else the bundled copy. So verdicts follow your own Claude Code updates and its default model, instead of whatever SDK version Probity pins (on one machine, the bundled 0.3.204 copy judged on `claude-opus-4-8`, the installed 2.1.306 on `claude-opus-5-5`). `executable` overrides this: `'installed'` (no fallback; with none found the verdict is "Claude judge unavailable", so a chain moves on), `'bundled'`, or a path. Probity's own judge, used when the config sets no `ai`, always runs the bundled copy; the templates set `ai: claudeJudge()` from 0.4.49. From 0.4.47 `model` picks the Claude model each verdict runs on, e.g. `claudeJudge({ model: 'claude-haiku-5-5' })`. Without it, the Claude Code that runs the judge picks its own default. A judge given a model is named `claude:<model>`, so `judgeChain` remembers it apart from the default one. A cheaper model is cheaper per verdict, but check how often it lets a retrofitted test through before using it for the TDD gate.
- **Pin the judge's model.** `claudeJudge()` with no `model` judges on the installed Claude Code's default model, so a project whose CLI defaults to Sonnet gets Sonnet verdicts. The TDD judge's rules were measured on Opus. In a JS/TS project whose judge ran on Sonnet, it made three kinds of mistake (#169–#171):
  - it denied with text concluding the write was allowed;
  - it counted tests already on disk, or one new test, as two new tests;
  - it refused an import sent alone before the code that uses it.

  Set `claudeJudge({ model: 'claude-opus-5-5' })`, or run a `shadowJudge` with an Opus candidate to measure the difference first. Deterministic shortcuts that skip the judge for such writes were tried and dropped: three reviews in a row got a test-weakening or behavior-changing write through them.
- **`judgeChain([...])`** asks each judge in order and uses the first one that is available, so the array order is the fallback order. It moves on only when a judge is unavailable: kiro-cli could not run, or Claude reports a spend limit, quota, rate limit or authentication failure. A real verdict, deny included, stands. Within one hook run, a judge that was just unavailable is skipped for the run's later verdicts (`skipUnavailableMs`), so one dead judge cannot use up the hook's time limit. From 0.4.28 the skip outlasts the hook run: `kiroJudge()` and `claudeJudge()` are named, and the chain keeps a named judge's "unavailable until" in a state file (`<tmpdir>/probity-kiro-judge/judge-chain.json` by default, `stateFile` to move it, `false` to keep it in memory). So a hung kiro-cli costs one write its `timeoutMs`, and later writes go straight to the next judge until the skip runs out. The last judge in a chain is always asked. A verdict that came from a fallback carries `meta.fallbackFrom` in the `--debug` trace: each earlier judge and why it didn't answer.
- **`shadowJudge(primary, candidates, { log })`** (from 0.4.48) measures other judges on the project's real traffic, without changing enforcement. Every verdict is asked of the primary and each candidate in parallel; the primary's verdict is the one returned, and the prompt and all verdicts are appended to `log` (JSONL, created `0600`). A candidate that throws, or hasn't answered `candidateTimeoutMs` (default 60 s) after the verdict started, is logged as such and never changes or blocks the verdict. A write waits for its slowest candidate up to that limit, and each candidate adds its own spend. Prompts contain the code being judged, so keep the log out of git; `includePrompt: false` logs only each prompt's SHA-256, at the cost of replaying later; `includePrompt: 'disagreements'` (from 0.4.57) keeps the prompt only where a candidate disagreed with the primary, the cases `--show` lists, which keeps a long-running log small. The report reads the log line by line, so its size isn't limited by memory. Probity's `--debug` trace can't do this: it records verdicts, not prompts.

  ```ts
  ai: shadowJudge(claudeJudge(), [claudeJudge({ model: 'claude-haiku-5-5' })], { log: '.probity/shadow.jsonl' }),
  ```

  After a week or so of normal work, `npx probity-shadow-report .probity/shadow.jsonl` prints, per candidate: how often it agreed with the primary; **leaks** (it passed what the primary denied, the enforcement a switch would lose) as a share of the primary's denials; **friction** (it denied what the primary passed) as a share of its passes; how often it or the primary was unavailable; median latency against the primary's; and tokens per model for both. Each rate comes with its 95% upper bound (one-sided Clopper-Pearson): no leak in 20 denials still allows a true leak rate near 14%, so a small sample cannot pass for a good result. `--show leaks|friction|all` lists each disagreement with its task, both reasons and the prompt hash, which finds the full prompt in the log. The primary is not ground truth either, so read the leaks rather than going by the agreement rate.

  From 0.4.50 the report also has a table **by judging task**, so it can show a candidate is good enough for one rule and not another (say the acceptance-language check but not the TDD gate). A judge sees only a prompt, never the rule that asked, so the presets run each rule labelled with its task, the innermost name of its wrapper chain (`characterizationTest(…(enforceTdd))` is `enforceTdd`), and `shadowJudge` logs the label. `withExtractionUnderGreen`'s own judge call is labelled `extractionUnderGreen`. From 0.4.51 the templates export `probityConfig({...})` in place of Probity's `defineConfig({...})`: the same config, with every rule it lists labelled, so a rule a project adds next to a preset is labelled too. With `defineConfig`, such rules are logged as `(unlabelled)` unless their list is wrapped in `withJudgeTasks([...])`. Verdicts logged before 0.4.50 are `(unlabelled)` too, and the report says how many verdicts have no task and how to label them. A rule that asks the judge a second, different question must label that call itself with `withJudgeTask('<task>', () => ctx.agent.reason(...))`, as `withExtractionUnderGreen` does; nothing detects a missing one.

The Kiro judge works when the call it judges comes from a live Kiro session (Kiro → shim → Probity → kiro-cli judge, checked for #86). In 7 nested sessions, 13 of 14 verdicts came from Kiro, median 15 s and at most 32.5 s; the first verdict of the first session timed out at 60 s and fell back to Claude. The judge inherits the parent session's environment (`KIRO_SESSION_ID` and the like) and still answered.

A committed config with `kiroJudge()` first still works on a checkout without kiro-cli: the chain finds kiro-cli missing in milliseconds and uses Claude. Expect Kiro verdicts to be slower, around 15 s typical and 42 s at worst against 8 s and 12 s on Claude. A write occasionally takes up to three verdicts, so leave the hook enough time: a hook that times out does not block, and in Claude Code the write then goes ahead unjudged. Claude Code's default limit for a command hook is 10 minutes, which is enough; don't set a lower `timeout` on the Probity hook. The Kiro shim template's `timeout_ms` is 300000 (5 minutes) from 0.4.20; an agent config copied from an earlier template has 120000, which three slow Kiro verdicts can exceed, so raise it.

**Updating:** once this is set up, run `/probity-update` to bring it forward instead of repeating these steps by hand — it upgrades the `@jjchill/probity-rules` package, proposes config migrations, refreshes the Kiro shim, and re-verifies scoping.

## Mental model

Deterministic rules are the cheap outer wall (pattern matches, no latency); AI-validated rules are the judgment layer behind it. **Rule order enforces that economics:** Probity stops at the first violation, so both Kotlin configs list every deterministic screen before any AI rule — a vendor import in core code is rejected free by the import screen, never after a TDD model call. Preserve that ordering when editing the configs; the workflow eval asserts it (deterministically-blocked steps must consult no AI validator). Each AI rule sends the validator a distilled version of the corresponding SKILL.md's rules plus the current file and the pending write, and gets back a pass/violation verdict. The prompts follow Probity's own `enforceTdd` conventions: judge the *change* rather than the whole file, never punish transient in-progress states, and treat an explicit user instruction to let a change through as authoritative — it's a guardrail, not a jail.

Customize the AI rules without forking them via `instructions: (defaults) => defaults + '...'` — e.g. name your project's core and adapter directories so `enforcePortsBoundary` infers file roles precisely.

## Evaluating the workflow

[`probity/evals/workflow-eval.ts`](probity/evals/workflow-eval.ts) evaluates the full enforcement stack as a **scripted episode**: a made-up feature (parcel tracking) is driven through the entire outside-in loop — glossary write, spec write, glossary-conflicting spec (blocked), UI-leaking spec (blocked), tagless acceptance test and a tag citing a nonexistent scenario (both blocked — spec-first at write time), acceptance test with Covers tag (fast-path verified), premature production code (blocked), red run, minimal implementation, vendor import in domain code (blocked), direct clock read (blocked), mocking-library import (blocked), commit before tests (blocked), commit on green (allowed), covered-scenario rename (blocked), wip promotion without a test (parity-blocked at commit, then baselined and allowed — the incremental-adoption path), used-term glossary rename (blocked), a backend-naming spec scenario (blocked — one language standard for specs and tests), a mutation-probe round-trip (probe allowed with no TDD call, commit blocked while the probe is on disk, allowed after reversion), unused-term retirement (allowed), a driver-scope round-trip (a `[system]`-tagged scenario: misspelled tag commit-blocked, tag without system-suite coverage commit-blocked, allowed once a thin system-driver test claims the scenario) — 48 steps, each asserting the expected decision and firing rule. Deterministically-blocked steps also assert that no AI validator was consulted, pinning the deterministic-before-AI rule order. Correctly blocked actions are not materialized, exactly as a real hook prevents them, so the episode's file state stays honest.

Scoping is part of what the episode exercises: the eval runs the rule entries exported by `probity.config.kmp.ts` itself (via its `kmpRuleEntries` factory), resolving each block's `files` globs with [`probity/rules/scoping.ts`](probity/rules/scoping.ts) — a pinned replica of Probity's picomatch matcher and glob anchoring. Four of the 48 steps are deliberately **out-of-scope** writes carrying content the core rules would block — a Room adapter with a vendor import and a real clock read, a Koin DI module, a mechanics-laden `TrackingRobot.kt` and its split-layout `TrackingViewModelDriver.kt` twin (the four-layer model's `*Dsl.kt`/`*Driver.kt` files are excluded alongside `*Robot.kt`) — and assert not just `allow` but that no AI validator was even consulted (`expectAiSilent`), so an eroded exclusion or over-broadened core glob in the template fails the eval instead of shipping.

Two modes:

(`hooks/probity/` carries its own `package.json` for this — run `npm install` there once so `tsx` and `@nizos/probity` resolve.)

- `npx tsx workflow-eval.ts` — scripted AI verdicts. CI-safe and deterministic: exercises the wiring, rule ordering, and every deterministic rule exactly; the AI rules' *invocation* is verified while their verdicts are assumed.
- `npx tsx workflow-eval.ts --live` — real verdicts via the `claude` CLI. Additionally evaluates the AI rules' prompt quality: does `enforceTdd` actually block the premature write and pass the post-red minimal one, does the Language Test catch the click-the-button scenario. Live mode asserts outcomes only (a write violating several rules may block on whichever rule runs first, as in a real session) and costs ~a dozen model calls.

What the harness does not cover: Probity's own engine — hook payload parsing and transcript adapters — and any drift between `rules/scoping.ts` and the engine's matcher across Probity upgrades (the replica exists because Probity doesn't export its matcher; it is pinned to a version and documents what to diff on upgrade). A mis-scoped glob in **your** edited config is the scope report's job (Setup step 4), not the eval's: run `npx probity-scope-report` against your real tree at setup and whenever the layout changes.

## Costs and caveats

- **AI rules cost a model call per matching write.** Scope tightly. `enforceTdd({ fastPath: true })` skips the AI when a write adds exactly one test (at the price of skipping refactor enforcement). Fast-paths must cover **every** rule scoped to a file or they buy nothing: a single-`@Test` write under `acceptance/**` fast-paths the TDD rule *and* — via `withAcceptanceLanguageFastPath` — the Language Test, provided the new test only reuses vocabulary already declared in the suite's DSL files and contains no mechanism words; anything novel falls through to the validator.
- **Edits to large files are sent to the judge as a diff** (from 0.4.59; #168). A write action carries the whole file, so a judge prompt held it twice, before and after, and a run of small edits to a large file resent it every time. Every preset now replaces those two sections with a unified diff and up to 20 unchanged lines either side of each change, plus the file's import and package lines wherever they are, when the file is at least 8,000 bytes, the prompt holds the exact sections (Probity's `enforceTdd` and most of this package's AI rules do), and the result is clearly smaller. Past 1,000 changed lines the file is sent whole. Rules still see the whole file, so deterministic checks are unchanged, and a new file is still sent whole. A one-line edit to a 45 KB file cut the TDD prompt from 100 KB to 13 KB. Tune it with the preset option `compactJudgeFiles: { minBytes, contextLines }`, or turn it off with `compactJudgeFiles: false`; outside a preset, wrap rules with `withCompactJudgeFiles(entries)`. To see whether it changes verdicts, run a `shadowJudge` with a candidate on the primary's model wrapped in `wholeFiles(...)`: that candidate is asked the uncompacted prompt, so its disagreements are the verdicts the diff alone decided differently. The shadow log records each compacted verdict's full and sent size, and `probity-shadow-report` prints how many verdicts were compacted and each candidate's agreement on compacted and whole prompts. A live shadow doubles judge cost. To check later instead (from 0.4.61; #174), set `compactJudgeFiles: { record: { log, sample: 0.1 } }`. A sampled share of compacted verdicts then records the whole-file prompt that wasn't sent, built locally with no model call, and the verdict the compacted prompt got. `npx probity-shadow-replay <log> [--judge claude|kiro] [--model ID] [--limit N] [--concurrency N] [--show leaks|friction|all]` later asks a judge those prompts, one call each, and prints the same agreement, leaks and friction as the report. By default it replays on the judge the recorded primary ran on, so disagreements measure compaction rather than a different model; a kiro primary's model isn't in its name, so pass `--model` if it wasn't kiro's default. A recorded prompt is about 120 KB, and it holds code and session context: keep the log local and out of git.
- **Agent support:** Probity supports Claude Code, GitHub Copilot CLI, and Codex natively, and Kiro through the shim in [`probity/kiro/`](probity/kiro/). Wherever the agent can be hooked, Probity is a required part of the install. The skills in this catalog also run in tools Probity cannot hook (Cursor, Gemini CLI, Windsurf, …); there the skills run without gates, so record that limitation in the project's agent instructions rather than assuming enforcement is live.
- **npm required** in the consuming project. The rules themselves are language-agnostic (they judge writes, not test runners), but `forbidInternalModuleMocks` recognizes jest/vitest specifically — extend `MODULE_MOCK_PATTERN` for other ecosystems.
- **Fail-closed:** if a rule throws or the AI validator is unavailable, Probity blocks. The custom rules return an explicit violation naming the misconfiguration when no AI agent is wired.
- **Capturing what the judge said:** add `--debug <path>` to the Probity hook command to append each hook payload and response to a file. When the judge answers in a malformed format twice, the response quotes its output in full, so the log holds what an issue report needs.
- **AI verdicts have variance.** The validator sees the pending file and the session transcript — not the definitions of types the file references — so it can occasionally deny on a wrong guess about a referenced type, and an identical re-replay may pass. Treat a surprising deny as worth one re-read of its reason before adapting; giving validators referenced-file access is an upstream improvement worth pursuing.
- **Each write is judged alone, against the file as it is on disk.** Dependent edits sent in parallel are each judged before the others land. For example, a call site that passes a new argument can be blocked while the edit adding that parameter goes through. Send dependent edits one after another: signature first, then call sites. The same goes for moving logic into a shared helper: extract it in place in the file that already holds it (the judge then sees the logic in the current file content), then call the helper from the new code path.
- **Override is in-session:** the agent can ask the user to wave a blocked change through, and the validator honors that on the next attempt. Softer than it sounds; it means disagreements surface to you instead of being silently forced either way.
- **These gates deter rationalization, not deliberate deception.** An adversarial replay trial (real iOS project, 20 fabricated events) confirmed the honest paths and also the limits: the green-run gate matches *recorded output*, so an echoed success banner or a re-read of a stale `.xcresult` satisfies it, and its "writes since the last run" index only advances on Write/Edit tool events — a file changed via shell redirection (`cat > file <<EOF`) is invisible. Treat the gates as guardrails for an agent trying to cut corners under pressure, and keep CI as the arbiter of record. Anchoring the gate to result-bundle freshness (compare the `.xcresult` timestamp against source mtimes) is the known upstream improvement.
- **Audit the write-rule globs against your real tree** (`npx probity-scope-report`). A write that no rule matches is a silent free pass, and layout surprises are common — the iOS trial found the app's `AppDelegate.swift` sitting *beside* `App/Sources/`, outside every glob, and an acceptance suite created in a new directory would be equally invisible. Scope rules to the *directory* that owns a layer, not to filename suffixes (`AcceptanceTests/**`, not `**/*Tests.swift` — a creative filename dodges a suffix; a test-method pattern inside the rule doesn't care what the file is called).
- **Division of labor, observed live:** the deterministic screens are trivially evaded by construction (`"XCUI" + "Application"` slips a regex), but in the same trial the AI TDD validator caught exactly that obfuscation, with an accurate explanation — while also being the layer that costs seconds and can't see files the globs exclude. Regexes are the cheap wall, AI is the judgment backstop, and neither substitutes for correct scoping.
